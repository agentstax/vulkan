Vulkan runs against the Postgres you already have — no broker, no new
infrastructure. This page takes you from an empty database to producing,
consuming, and inspecting messages, ending with the headline: producing a
message in the same transaction as your own writes.

You write two constructors: the connection pool and the client over it.
The pool stays yours to close; topics, producing, and consuming are calls
on the client. Nothing on this page is pseudocode; every sample compiles
against the shipped library.

<ThreadAside label="NOTE" title="Prerequisites">
You need a Postgres connection and Go 1.27+. Vulkan's test suite runs
against Postgres 17. Tables are created in your database's default schema
by Vulkan itself — there is no SQL migration file to apply by hand.

</ThreadAside>

1. **Install the library and CLI**

   ```sh
   go get github.com/agentstax/vulkan
   go install github.com/agentstax/vulkan/cmd/vulkan@latest
   ```

   The CLI is a separate module, so cobra and friends never enter your
   application's dependency graph.

2. **Create the control-plane schema**

   ```sh
   export VULKAN_ADMIN_DATABASE_URL='postgres://app_user:secret@localhost:5432/app_db'
   vulkan migrate init
   ```

   `migrate init` creates the shared control-plane tables (the topic
   catalog, the worker fleet) at their baseline. It is idempotent — a no-op
   against a database that already has them. The same thing happens in code
   the first time `RegisterTopic` runs against an empty database, so the
   CLI step is a convenience, not a requirement. `RegisterSystem` stays the
   explicit call for setting the system's own knobs — the built-in alert
   schedules — and is safe to run on every startup.

3. **Register a topic and produce a message**

   A topic is registered once by name; producing is then a typed call.
   Your payload type is a plain Go struct, stored as JSONB, and it
   declares its own schema version — the number written on every row it
   produces ([schema versions](/guides/schema-versions/)).

   ```go
   package main

   import (
   	"context"
   	"fmt"
   	"os"

   	"github.com/agentstax/vulkan/pkg/datastore"
   	vulkan "github.com/agentstax/vulkan/pkg/vulkan"
   )

   type WelcomeEmail struct {
   	UserId string `json:"user_id"`
   }

   func (WelcomeEmail) SchemaVersion() int { return 1 }

   func main() {
   	ctx := context.Background()

   	ds, err := datastore.NewPostgresDatastore(ctx, "app_user", "localhost", "app_db",
   		&datastore.PostgresConnectionConfig{Pass: os.Getenv("PGPASSWORD")})
   	must(err)
   	defer ds.Close()

   	client, err := vulkan.NewClient(ds, nil)
   	must(err)

   	registered, err := client.RegisterTopic(ctx, "signup.welcome-email",
   		&vulkan.TopicConfig{})
   	must(err)

   	instance, err := client.RegisterProducer[WelcomeEmail](ctx, registered.Name, nil)
   	must(err)

   	produced, err := instance.Produce(ctx, &WelcomeEmail{UserId: "user-123"}, nil)
   	must(err)
   	fmt.Printf("produced message id=%d\n", produced.Id)
   }

   func must(err error) {
   	if err != nil {
   		fmt.Println(err.Error())
   		os.Exit(1)
   	}
   }
   ```

   `RegisterTopic` is idempotent, and it creates the topic's own physical
   tables — its message log, exception queue, and cursor tables — in the
   same call. Registering the system first is required; a topic cannot
   exist without the control plane it rides on.

4. **Consume it**

   Consumption is a consumer group: an independent reader with its own
   cursor, its own retry budget, and its own dead-lettered messages. The
   handler receives your typed payload; returning an error schedules a
   retry with exponential backoff (`vulkan.Terminal` and
   `vulkan.Delay` are the other two answers —
   [handler outcomes](/guides/handler-outcomes/)).

   ```go
   package main

   import (
   	"context"
   	"fmt"
   	"os"
   	"time"

   	"github.com/agentstax/vulkan/pkg/datastore"
   	vulkan "github.com/agentstax/vulkan/pkg/vulkan"
   )

   type WelcomeEmail struct {
   	UserId string `json:"user_id"`
   }

   func (WelcomeEmail) SchemaVersion() int { return 1 }

   func main() {
   	ctx, stop := vulkan.LifecycleContext(nil)
   	defer stop()

   	ds, err := datastore.NewPostgresDatastore(ctx, "app_user", "localhost", "app_db",
   		&datastore.PostgresConnectionConfig{Pass: os.Getenv("PGPASSWORD")})
   	must(err)
   	defer ds.Close()

   	client, err := vulkan.NewClient(ds, nil)
   	must(err)

   	registered, err := client.Topic("signup.welcome-email").Get(ctx)
   	must(err)
   	if registered == nil {
   		fmt.Println("topic not registered -- run the producer first")
   		os.Exit(1)
   	}

   	instance, err := client.RegisterConsumer[WelcomeEmail](ctx, "email-sender", registered.Name, nil,
   		&vulkan.ConsumerConfig{
   			Message: &vulkan.MessageOptions{
   				Timeout: 5 * time.Second,
   				Retry:   &vulkan.RetryPolicy{MaxRetries: 3, BaseDelay: time.Second},
   			},
   		})
   	must(err)

   	must(instance.Consume(ctx, func(ctx context.Context, email *WelcomeEmail) error {
   		fmt.Printf("sending welcome email to %s\n", email.UserId)
   		return nil
   	}))
   }

   func must(err error) {
   	if err != nil {
   		fmt.Println(err.Error())
   		os.Exit(1)
   	}
   }
   ```

   Two things here are load-bearing:

   - `vulkan.LifecycleContext` wires SIGINT/SIGTERM into the context.
     `Consume` requires a cancellable context — it refuses
     `context.Background()` — because graceful shutdown is part of the
     contract, not an option. Ctrl-C drains cleanly.
   - The `nil` bindings argument to `RegisterConsumer` is the group's
     binding set: `nil` means the whole topic. Handlers should be idempotent —
     redelivery after a crash or timeout is normal at-least-once behavior.

5. **Look inside with psql**

   Everything is rows in your database. Each topic owns its physical
   tables, named by the topic's id
   ([the whole map](/concepts/table-design/)) — resolve it once from
   the catalog:

   ```sql
   SELECT id FROM topic_config WHERE name = 'signup.welcome-email';
   ```

   Say it returned `1`. Then (make your handler return an error and
   produce a few messages first, if you want something to watch):

   **Your messages**

   ```sql
   SELECT id, payload, created_at FROM message_log_1 ORDER BY id;
   ```

   **Delivery status**

   ```sql
   SELECT g.name AS consumer_group, d.status, count(*), max(d.attempts) AS attempts
   FROM exception_queue_1 d JOIN consumer_group_config g ON g.id = d.consumer_group_id
   GROUP BY 1, 2;
   ```

   **Dead-lettered**

   ```sql
   SELECT d.message_id, m.payload, d.attempts, d.last_error
   FROM exception_queue_1 d JOIN message_log_1 m ON m.id = d.message_id
   WHERE d.status = 'dead';
   ```

   **Attempt history**

   ```sql
   SELECT message_id, attempt, status, error, attempted_at
   FROM delivery_log_1 ORDER BY message_id, attempt;
   ```

   Watch `attempts` climb and `can_run_after` push into the future with
   backoff; after the retry budget is spent the row's status becomes
   `dead`, with the payload and `last_error` intact — nothing expires
   behind your back. One honesty note: a delivery that *succeeds* is
   deleted, not kept — the exception queue shows in-flight and failed
   work, while every failed attempt is preserved in the `delivery_log_1`
   audit trail.

6. **The headline: produce inside your own transaction**

   The closure you pass to `ProduceFunc` runs inside the message's own
   transaction. Your business write and the message commit together, or
   neither does — the message can never exist for a rolled-back signup,
   and never be lost for a committed one.

   ```go
   produced, err := instance.ProduceFunc(ctx,
   	func(ctx context.Context, tx vulkan.Tx, _ string) (*WelcomeEmail, error) {
   		if _, err := tx.Exec(ctx, `INSERT INTO users (id) VALUES ($1)`, "user-123"); err != nil {
   			return nil, err
   		}
   		return &WelcomeEmail{UserId: "user-123"}, nil
   	}, nil)
   ```

   To produce to several topics atomically, `vulkan.InTransaction` opens
   one transaction and hands your closure a `Tx` that each instance's
   `ProduceInTx` accepts. Do your own statements first and produce last:
   producing holds a lock on consumer progress for the topic until commit,
   so the produce should be the shortest-held thing in the transaction.
   The whole story — proving the rollback to yourself, multi-topic
   commits, and what stays yours — is
   [the transactional-produce guide](/guides/transactional-produce/).

<ThreadAside label="CAUTION" title="One more thing for real deployments">
Topic upkeep — creating partitions ahead, enforcing retention, advancing
the committed cursor — runs while a consumer is running, or under the
standalone manager: `vulkan manager run`. A deployment that only produces
should run the manager alongside it.

</ThreadAside>

## Start with the problem you actually have

You don't need a message platform today. You need to send a welcome
email after signup, process a Stripe webhook, resize an upload —
*reliably*. That usually means adding Redis or SQS to your stack before
lunch. With Vulkan it means adding nothing:

```go
// In your signup handler — the user INSERT and the message commit
// together, so the email work exists if and only if the user does:
produced, err := emails.ProduceFunc(ctx,
	func(ctx context.Context, tx producer.Tx, _ uuid.UUID) (*WelcomeEmail, error) {
		if _, err := tx.Exec(ctx, `INSERT INTO users (id) VALUES ($1)`, user.Id); err != nil {
			return nil, err
		}
		return &WelcomeEmail{UserId: user.Id}, nil
	}, producer.ProduceOptions{})

// Anywhere in your app (or a separate binary) — the consumer:
err = instance.Consume(ctx, func(ctx context.Context, email *WelcomeEmail) error {
	return mailer.SendWelcome(ctx, email.UserId)
})
```

One library, your existing Postgres, explicit setup you can read in
full on the [quickstart](/quickstart/). Retries with exponential
backoff and dead-lettered messages you can `SELECT` are config, not
add-ons — and because the message is produced **in your transaction**,
the email can never fire for a signup that rolled back, and never get
lost for one that committed. That last guarantee is structurally
impossible with Redis, SQS, or any other external queue.
[Why →](/guides/transactional-produce/)

## You will outgrow a job queue. You won't outgrow this.

Here's the thing about every async tool you could pick today: it's a
fork in the road you can't see yet. The job queue can't fan out. The
queue service can't hand history to a new service. Eighteen months in,
each new need means bolting on another system. Vulkan's bet: **a queue
is just a topic with one consumer group** — so growing never means
migrating.

<Steps>

1. **Day 1 — background work.** The code above. One topic, one consumer
   group, retries and dead-lettering included. As capable as any job
   queue, with one guarantee none of them have.

2. **Month 3 — a second consumer.** Product wants an in-app activity
   feed fed by the same signups. With a job queue, the message is
   deleted the moment the email handler finishes — there's nothing left
   to consume. In Vulkan, your queue was a retained log all along:

   ```go
   feed, err := feedConsumer.Register(ctx, "activity-feed",
       registered.Name, topic.SchemaVersion(1), nil)
   ```

   Independent cursor, independent retries, independent dead-lettered
   messages. The email group never notices.

3. **Month 9 — a new service needs history.** You're building search.
   Register a new group and it reads everything retention still holds —
   that's simply a new group's default — then arrives at live traffic.
   No hand-written backfill, no consistency scramble.

4. **Year 1 — routing and per-key work.** Multiple message types,
   regional consumers, a per-account exclusivity requirement. Routing
   keys, bindings, and per-key concurrency control are already in the
   tables:

   ```go
   produced, err := instance.Produce(ctx, &OrderCreated{OrderId: order.Id},
       producer.ProduceOptions{RoutingKey: "orders.eu.created"})

   compliance, err := auditConsumer.Register(ctx, "eu-compliance",
       registered.Name, topic.SchemaVersion(1), []string{"orders.eu.*"})
   ```

</Steps>

Same tables the whole way. Each step is *additive* — a line of code,
not a migration project, not a second system, not a third. This is the
point where other tools hand you a Kafka cluster and a sympathetic
look.

## Open source. Everything is a query.

The engine is open source — run it against any Postgres: yours, RDS,
Neon, Railway, Supabase. And because the entire state is rows, your
messaging layer answers questions like a database — because it is one:

```sql
-- 2am, something's off. "What happened to order ord_8431?" is a
-- query, not an archaeology dig through a broker console:
SELECT g.name AS consumer_group, d.status, d.attempts, d.last_error
FROM message_log_1 m
JOIN delivery_1 d ON d.message_id = m.id
JOIN consumer_group g ON g.id = d.consumer_group_id
WHERE m.payload->>'order_id' = 'ord_8431';
```

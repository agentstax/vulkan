<ThreadAside label="PROPOSED" title="vulkan demo does not ship yet">
`vulkan demo` does not ship yet. This page is the product proposal for
it — and it's a thin one, because the attacks below are the
failure-injection labs the engine is *actually developed against*
(kill -9 mid-process, crash mid-commit, expired-lease reclaim). The
demo is those labs, packaged so you can run them yourself.

</ThreadAside>

Every messaging system claims durability. Claims are cheap. The demo's
entire purpose is to let you **attack** Vulkan — because durability is
the one product quality you can verify with your own hands in five
minutes, and we'd rather you trust the experiment than the brochure.

```sh
# PROPOSED — not a shipped command.
vulkan demo --chaos
```

One command would spin up a disposable Postgres (Docker), a topic
called `orders`, three consumer instances, and start producing 5,000
messages. The scoreboard tracks three numbers — **produced, resolved,
lost** — and the demo prints suggestions for ways to hurt it. Your goal
is to make `lost` read anything but zero.

## The attacks


1. **Kill a consumer instance mid-message.**

   ```sh
   kill -9 $(pgrep -f vulkan-demo-consumer-2)
   ```

   Instance 2 dies holding a claimed range, with no chance to clean
   up — no shutdown hook, no rollback call, nothing. Watch the
   scoreboard: its lease expires, the next claim by any surviving
   instance reclaims the range before taking fresh work, `lost` stays
   0.

   There is no recovery code running. The expiring lease *is* the
   failover — a property of the data, not of any process that can die.
   [How leases work →](/concepts/lifecycle/)

2. **Crash mid-commit, deterministically.**

   Suspect the `kill` timing was lucky? Make the instance betray you on
   purpose:

   ```sh
   vulkan demo consumer --crash-after 3   # os.Exit(1) mid-transaction, every 3rd message
   ```

   A consumer that *always* dies at the worst possible moment, forever.
   The topic still drains. `lost: 0`.

3. **Fail messages randomly.**

   ```sh
   vulkan demo consumer --fail-rate 0.3 --retries 3
   ```

   Now 30% of handler calls return errors. Watch failed messages get
   their delivery rows, retry with exponential backoff, and — for the
   stubborn ones — land in `dead`: *visible, counted, and queryable*,
   not discarded:

   ```sql
   SELECT count(*) FROM exception_queue_1 WHERE status = 'dead';
   ```

   Dead-lettered messages aren't lost messages. They're messages
   waiting for you, payload and error history intact.
   [Triage them →](/guides/dead-letters/)

4. **Go for the database.**

   ```sh
   docker restart vulkan-demo-postgres
   ```

   The one everyone assumes is cheating. Consumer instances lose their
   connections, back off, and reattach when Postgres returns; every
   in-flight message was either committed (resolved, exactly as
   recorded) or not (claimable again). Postgres's crash recovery has
   been hardened for thirty years — that's the point of building on it
   instead of beside it.

5. **The cruelest one: the zombie.**

   ```sh
   vulkan demo consumer --sleep 30s   # processing takes longer than the lease
   ```

   The instance isn't dead — just slow. Its lease expires, the range is
   reclaimed, another instance processes the message… and then the
   zombie finishes too. The same message processed **twice**. The
   scoreboard calls it out.

   This isn't a Vulkan bug; it's the honest physics of distributed
   delivery — the same trade SQS and Pulsar make. The demo *induces* it
   so you design idempotent handlers knowing it's real, instead of
   discovering it in production.
   [At-least-once, and proud of it →](/concepts/lifecycle/)


## The finale: three groups, one log

```sh
vulkan demo synthesis
```

The part that shows why Vulkan is a *platform*, not a queue. On a
single topic, simultaneously:

- group **A** retries message #5 three times and dead-letters it,
- group **B** processes message #5 without incident — and writes no
  per-message state at all doing it,
- group **C**, registered after the run started, reads the whole
  retained history from the beginning — which is simply what a new
  group does.

Per-group failure state, shared immutable log, independent cursors —
the combination that normally requires running a queue *and* a log
*and* glue. [Why that's hard everywhere else →](/concepts/queue-and-log/)

## The scoreboard never lies

The counters aren't instrumentation we control — they're SQL against
the same tables your application would use, printed by the demo so you
can run them yourself in `psql` mid-attack:

```sql
SELECT
  (SELECT count(*) FROM message_log_1)                           AS produced,
  (SELECT min(committed) FROM consumer_group_cursor_1)           AS resolved_through,
  (SELECT count(*) FROM exception_queue_1 WHERE status = 'dead') AS dead_lettered;
```

`committed` is the load-bearing number: every message at or below it
either ran clean or sits in `dead` with its error recorded. "Lost"
would be a message the cursor passed with neither — and the demo's
assertion, like the labs', is that there are none.

Vulkan has no broker process. The "server" is your Postgres database;
the "clients" are your own application processes running the Vulkan
library. Everything below is rows.

```
                     ┌──────────────────────────────────────────────────┐
                     │                     POSTGRES                     │
  producers          │                                                  │      consumers
                     │  shared control plane:                           │
  app ──produce────▶ │    topic_config · consumer_group_config          │
  app ──produce────▶ │    worker_config · schedule_config               │
    (in your txn)    │                                                  │
                     │  one table family per topic (suffix = topic id): │
                     │    message_log_1  immutable log, id-partitioned  │ ◀──claim ranges── instance
                     │    consumer_group_cursor_1  claimed / committed  │ ◀──claim ranges── instance
                     │    binding_config_1   routing patterns           │
                     │    exception_queue_1  failure lifecycle          │ ◀──retry claims── instance
                     │    delivery_log_1  per-attempt audit trail       │
                     │    claim_lease_1 · message_key_lease_1           │
                     │    compaction_head_1 · idempotency_key_1         │
                     └──────────────────────────────────────────────────┘
```

## Two kinds of table

**The shared control plane** — created once by `RegisterSystem`, which
the first `RegisterTopic` against an empty database runs automatically
(or `vulkan migrate init`): the topic catalog (`system_config`,
`topic_config`, `topic_config_log`, `consumer_group_config`), the
worker fleet (`worker_config`, `worker_config_log`, `worker_instance`,
`schedule_config`, `schedule_cursor`), and migration history
(`migration_log`).

**One physical family per topic** — created by `RegisterTopic`, named
by the topic's id. A per-topic table carries no `topic_id` column; the
table name *is* the scope — every table, key, and relationship is
mapped on [Table Design](/concepts/table-design/). The split is
deliberate, not decorative:

- Retention drops wait on every cursor in a table — shared tables would
  let one lagging group on topic A block cleanup for unrelated topic B.
- A failure outage churns `exception_queue` with inserts and deletes —
  shared, that churn would slow every other topic's claims.
- Destroying a topic is `DROP TABLE` on its family, not a cross-table
  `DELETE` sweep.

The core of the family:

**`message_log_<id>` — the log.** Append-only, never mutated by
consumption; the bigserial `id` is the position. It is **partitioned by
id range** (`PartitionSize` rows per partition, default 1M): the
producer creates the next partition ahead as the current one fills, and
retention expires whole partitions with a `DROP` — no million-row
deletes, no vacuum debt.

**`consumer_group_cursor_<id>` — the happy path.** One row per consumer group:
`claimed` (the read frontier) and `committed` (everything at or below
it is resolved). Consumer instances claim contiguous *ranges* of the
log under a lease; messages that succeed are simply swept past. Fan-out
to another group costs one more cursor row, and per-group **lag** is
`max(id) - committed`.

**`exception_queue_<id>` — the failure lifecycle.** One row per *failed*
message per group: status, attempts, backoff timestamp, last error,
lease. The [state machine](/concepts/lifecycle/) lives here, claimed
with `FOR UPDATE SKIP LOCKED` so any number of instances compete
safely. `delivery_log_<id>` keeps the per-attempt audit trail beside
it.

**`binding_config_<id>` — the routing.** Which groups receive which messages,
decided when deliveries materialize, by matching the message's routing
key against stored patterns ([routing →](/concepts/routing/)).

## The flow of one message

1. **Produce.** One `INSERT` into the topic's message log — optionally
   inside *your* transaction, next to your business writes
   ([the headline →](/guides/transactional-produce/)). Commit makes it
   durable and visible, atomically.
2. **Claim.** A consumer instance advances the group's `claimed` cursor
   over a range and takes a lease on it; bindings and compaction filter
   what the range hands the handler. The claim commits instantly and
   the handler runs unlocked — a ten-minute handler never holds a
   database lock.
3. **Resolve.** Success: nothing to write; the committed cursor sweeps
   past. Failure: an exception-queue row materializes and retries with backoff
   until it succeeds (row deleted) or exhausts its budget (`dead`).
   Instance crashed? Its lease expires and the range is reclaimed —
   recovery is a property of the data, not of any process that can die.

<ThreadAside label="NOTE" title="Consumers poll — by design, for now">
There is no `LISTEN/NOTIFY` anywhere in the library. Claims poll
(`ClaimPollRate`, default 5s), which keeps the mechanism to one moving
part and covers backoff-delayed work for free. Produce-triggered
wake-ups with a fallback poll are a designed proposal, deliberately
deferred until polling latency is a *measured* problem.

</ThreadAside>

## The maintenance fleet

Upkeep runs as **workers** — rows in the `worker_config` table, claimed and
executed by whatever processes are around. Every `Consume` runs the
system manager, which reconciles the fleet; a deployment that only
produces runs `vulkan manager run` instead, and
`ClientConfig.DisableManager` opts a process out. Replicas coordinate
through worker claims, so running N copies is safe.

| Worker | Maintains |
| --- | --- |
| `topic_janitor` | drops/sweeps expired partitions, idempotency keys, message-key leases |
| `cursor_advancer` | advances each group's `committed` behind resolved work |
| `consumer_group_janitor` | sweeps superseded binding declarations |
| `schedule_producer` | produces one request per due schedule |
| `metrics_collector` | snapshots lag, backlog, and delivery state as metrics |
| `alert.*` checks | publish operator warnings to the `__system.alerts` topic |

## Costs, honestly

Failure costs writes: a message that fails gets an exception-queue row, a log
row per attempt, and updates per retry. Success costs almost nothing
per message — the cursor advance amortizes over the whole range. That
inverts the usual per-subscription trade (Pulsar pays per-message
per-subscriber always; Kafka never pays and therefore can't express
per-message state).

Throughput and latency numbers are deliberately absent from this page:
the benchmark pipeline that will back them is
[in progress](/roadmap/), and until a number has a recorded run behind
it, we don't print it. Postgres compatibility: the test suite runs
against Postgres 17, and PG-18-only syntax is deliberately avoided.

The mark of a healthy message architecture: **producers don't know
consumers exist.** A producer states what happened, tagged with a routing
key; each consumer group declares which keys it cares about. In Vulkan
that declaration is a **binding** — a stored pattern matched against the
message's routing key when the group's deliveries materialize.

## Produce with a routing key

```go
produced, err := instance.Produce(ctx, &OrderCreated{OrderId: order.Id},
	producer.ProduceOptions{RoutingKey: "orders.eu.created"})
```

The key is optional. A message produced without one is received only by
groups that declared no bindings — it carries nothing for a pattern to
match.

## Declare the group's bindings

A group's bindings are declared as a whole set, in `Register`'s last
argument — there is no separate bind verb to call one pattern at a time:

```go
// Receipts care about created orders.
receipts, err := emailConsumer.Register(ctx, "email-receipts",
	registered.Name, []string{"orders.*.created"})

// EU compliance wants everything EU.
compliance, err := auditConsumer.Register(ctx, "eu-compliance",
	registered.Name, []string{"orders.eu.*"})

// The analytics group passes nil: no bindings, the whole topic.
analytics, err := statsConsumer.Register(ctx, "order-analytics",
	registered.Name, nil)
```

Produce `orders.eu.created` → `email-receipts`, `eu-compliance`, and
`order-analytics` all receive it; a `us-warehouse` group bound to
`orders.us.*` hears nothing. The producer changes zero lines when a new
group comes online.

## The pattern language: one wildcard, honestly scoped

`*` matches **any run of characters** — including dots. The pattern is
anchored at both ends; everything else is literal:

| Pattern | `orders.eu.created` | `orders.us.central1.created` | `orders.eu.updated` |
| --- | --- | --- | --- |
| `orders.*.created` | matches | matches — `*` crosses depth | no |
| `orders.eu.*` | matches | no | matches |
| `orders.*` | matches | matches | matches |

Note the second column: `*` is a true wildcard, so a pattern cannot pin
an exact segment depth ("exactly one segment here"). If you need to keep
hierarchies apart, make the literal parts distinctive. A NATS-style
one-segment wildcard is a possible future refinement, not a shipped
behavior.

## How a set change lands

Bindings are per-group state that many deployed instances declare, so
declaration has explicit outcomes rather than last-writer-wins:

- **installed** — the declared set is now the group's effective set (the
  first declarer, or nothing live disagrees).
- **joined** — the declared set was already stored; nothing to change.
- **waiting** — a live instance still declares a *different* set. The
  waiting instance retries (every `BindingRetryInterval`, default `10s`)
  until the disagreeing instances go away — a deploy rolling out a new
  binding set converges as the old instances stop.

Inspect where every group stands:

```sh
vulkan alert bindings
```

<ThreadAside label="NOTE" title="Binding changes are forward-only">
The pattern is evaluated when a message
[fans out](/concepts/fan-out/) to the group, and the
fan-out position only moves forward — so a binding added today applies
to messages produced after it installs. Messages already routed (or
skipped) keep the outcome they had.

</ThreadAside>

## It's all rows

Each topic owns a physical binding_config table, named by the topic's id
([table design](/concepts/table-design/)). The
`pattern` column keeps the pattern as you wrote it; the POSIX
translation it matches with sits beside it as `pattern_regex`:

```sql
SELECT g.name AS consumer_group, b.pattern
FROM binding_config_1 b JOIN consumer_group_config g ON g.id = b.consumer_group_id
ORDER BY 1;
```

Every declaration attempt — installed and waiting alike — is also
appended to the topic's `binding_config_log` table with who declared it and
when, so "who changed the routing and when" is a query, not a mystery.

## What routing is not (yet)

Matching is on the routing key only. Header or content matching
("`region=eu` AND `tier=gold`" over a JSONB attribute set) is a designed
follow-up that waits for a real workload — today, encode what you route
on into the key.

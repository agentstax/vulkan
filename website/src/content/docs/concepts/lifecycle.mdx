Vulkan's consumer is built on an asymmetry worth understanding: **a
message that succeeds never gets its own row.** Consumer instances claim
contiguous *ranges* of the message log under the group's cursor, run your
handler over each message, and the cursor sweeps past everything that
went cleanly — zero per-message bookkeeping on the happy path.

State materializes exactly when something goes wrong. A handler error
writes the message its own **delivery row**, and that row is a state
machine:

```
  handler returns an error
            │  the message gets its own delivery row
            ▼
        ┌───────┐    claimed, attempts + 1     ┌──────────┐
        │ ready │ ───────────────────────────▶ │ inflight │
        └───────┘                              └──────────┘
            ▲                                   │        │
            │ lease expired — reclaimed         │        │ retry succeeds
            ├───────────────────────────────────┤        ▼
            │ retry fails, attempts left        │    row DELETED
            └─── can_run_after = now + backoff ◀┤
                                                │ retry fails, attempts spent
                                                ▼
                                            ┌──────┐   dead-lettered: payload,
                                            │ dead │   attempts, and last_error
                                            └──────┘   all kept, all queryable
```

The handler has two more answers than nil-or-error.
`vulkan.Terminal(err)` skips the retries and writes the row
`dead` on this attempt; `vulkan.Delay(d)` writes a `ready` row
with `can_run_after` = now + `d` and counts it in `delays`, not as a
failure. [Handler outcomes](/guides/handler-outcomes/) has the table.

All of it is **per consumer group**. Group A dead-lettering message 5
doesn't affect group B — for group B the message never even had a row.
And a `dead` row never blocks the group's cursor: the rest of the topic
keeps flowing past it.

Every transition is also appended to the topic's `delivery_log` audit
trail — by default every outcome except success (the topic's
`DeliveryLogMode` can widen that to successes too, or turn it off).

## Retries & backoff

The retry budget and curve are ordinary config — set once on the
consumer group, or requested per message at produce time (messages *request*,
consumers *clamp*):

```go
fraud, err := client.RegisterConsumer[OrderPlaced](ctx, "fraud-scoring", "orders.placed",
	&vulkan.ConsumerConfig{
		Message: &vulkan.MessageOptions{
			Timeout: 30 * time.Second,
			Retry:   &vulkan.RetryPolicy{MaxRetries: 5, BaseDelay: 2 * time.Second},
		},
	})
```

The delay before attempt *n* is `BaseDelay × Exponent^n`, capped at
`MaxDelay` (defaults: exponent 2, cap 5 minutes, 3 retries, `30s`
timeout). What the timeout actually does when it fires — and the
goroutine it can leave behind — is its own page:
[Consumer Timeouts](/guides/consumer-timeouts/). And backoff is a **timestamp, not a timer**: a failed retry
writes `can_run_after` into the future and the row simply becomes
claimable again when the time comes. Nothing is waiting in a process
that might die.

## Leases: surviving dead consumers

A claim takes a **lease** — a row with an expiry, not a database lock.
Two kinds cover the two tiers:

- **Range leases** cover healthy claims. A consumer instance that
  vanishes — OOM-killed, deploy, kernel panic — leaves its range's lease
  to expire; the next claim by any instance reclaims crashed ranges
  *before* taking fresh work, so those messages drain first. A range
  reclaimed too many times (3 by default) is **quarantined** into
  individual delivery rows instead of handed out again — one poison
  message can't crash-loop a whole range forever.
- **Per-row leases** cover retries. An `inflight` row whose lease
  expired is claimable again. And as a backstop, an expired row that is
  *also* out of attempts is marked `dead` with
  `[killed: crash-loop hit max attempts]` appended to its error — a
  handler that kills its process every time can't loop forever.

No heartbeat protocol, no session state, no rebalancing storm. Expired
leases are reclaimed by the same claim queries that do the normal work.

<ThreadAside label="CAUTION" title="At-least-once, and proud of it">
Leases mean a slow-but-alive handler and a reclaim can occasionally both
process the same message — the same trade SQS, Pulsar, and every real
queue makes. Vulkan is honest about being **at-least-once**: write
idempotent handlers. `vulkan.MetaFromContext(ctx)` gives you the
message id inside your handler — a natural idempotency key. Systems that
promise exactly-once delivery are selling you exactly-once *something
else*.

</ThreadAside>

## Dead-lettered messages are a query

After the retry budget is spent, the row's status is `dead` — with the
payload still joined to the log, the attempt count, and the final error:

```sql
SELECT m.payload, d.attempts, d.last_error, d.updated_at
FROM exception_queue_1 d
JOIN message_log_1 m ON m.id = d.message_id
JOIN consumer_group_config g ON g.id = d.consumer_group_id
WHERE g.name = 'fraud-screening' AND d.status = 'dead'
ORDER BY d.updated_at DESC;
```

No separate dead-letter queue to provision per consumer, and nothing
expires behind your back — dead rows live until the retention drop that
removes their message log rows.

<ThreadAside label="PROPOSED" title="A redrive verb">
Today there is no API to reset dead rows to `ready` after you fix the
bug — a first-class redrive verb is a proposed capability, not a shipped
one. The [dead-letters guide](/guides/dead-letters/) covers the triage
workflow that exists now.

</ThreadAside>

## Why this matters

This per-message failure lifecycle is precisely what the log world can't
express — a Kafka consumer's *only* state is "I have read up to offset
N." One poison message and your choices are: stall the partition, skip
and lose it, or build a parallel retry-topic system by hand. Vulkan's
answer is a cursor for the 99.9% that succeeds and a state machine for
the 0.1% that doesn't — native, per group, and visible in `psql`.

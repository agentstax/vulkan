Ordering and concurrency are fundamentally at odds: if message B must
wait for message A, no amount of consumer instances makes B faster.
Systems that pretend otherwise either serialize everything (slow) or
order nothing (wrong). This page says exactly which trade Vulkan ships
today — and which one is still a proposal.

## What's guaranteed by default

Messages are appended with strictly increasing ids, and a group's claims
scan the log **in id order** — work is handed out oldest-first. But
handed out is not finished: with `MessageConcurrency` above 1, multiple
consumer instances, or a retry in the mix, *completion* order is not
guaranteed. The default is full parallelism, honestly labeled.

## Opt-in: one in-flight delivery per key

For messages that carry a compaction key, `ConcurrencyDefer` gives you
per-key mutual exclusion within a consumer group:

```go
compaction, err := producer.NewCompactionOptions("acct-42", 0)
if err != nil {
	return err
}
produced, err := instance.Produce(ctx, &BalanceAdjusted{Account: "acct-42", Delta: -500},
	producer.ProduceOptions{
		Compaction: compaction,
		Message:    &common.MessageOptions{Concurrency: common.ConcurrencyDefer},
	})
```

The guarantee: **at most one delivery per compaction key is in flight
at a time, per consumer group.** Under the hood it's a `key_lease` row —
a same-key message arriving while the key is busy is recorded `deferred`
and picked up later; messages with different keys, and messages with no
key, run fully parallel.

The subtlety that makes this *not* FIFO: compaction semantics apply.
When the key frees, the key's **current head** runs — the latest
version, not every version ever written. If three updates to `acct-42`
land while the first is processing, the middle one is superseded and
only the newest runs. That's "process each key's current state, one at
a time" — exactly right for state-shaped messages (a user record, a
session, a device's latest reading), and exactly wrong for "apply every
delta in sequence."

The hot-key trade comes with it, visibly: a hot key serializes itself.
Same-key produces commit one after another, and adding producer
processes makes a hot key slower, not faster — that's what you opted
into.

<ThreadAside label="PROPOSED" title="Strict per-key FIFO">

"Every message with this key, in order, one at a time" — a separate
partition key beside the compaction key, with claim-time lanes and
order preserved through retries — is a designed-but-unbuilt proposal
(the SQS `MessageGroupId` / Kafka partition shape). It's deliberately
not the same knob as compaction: compaction answers "what's current,"
FIFO answers "don't reorder history." If your workload needs the
second, today Vulkan doesn't ship it.

</ThreadAside>

## Compared to the neighbors

Scored on shipped behavior only:

| | Kafka | SQS FIFO | Vulkan today |
| --- | --- | --- | --- |
| Ordering unit | partition (count fixed up front) | MessageGroupId | compaction key |
| Guarantee | per-partition order | per-group order | per-key exclusivity, latest version wins |
| Choose per message? | no — topic topology | yes | yes |
| Unordered fast path on the same topic | no | no — separate queue | yes — messages without a key |

Strict per-key FIFO would move Vulkan's guarantee column next to SQS
FIFO's; until it ships, it's a proposal, not a checkmark.

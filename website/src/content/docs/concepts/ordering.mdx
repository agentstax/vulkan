---
title: Ordering & Concurrency
description: What order Vulkan actually guarantees, and the two per-key policies you can opt into — exclusive and ordered.
---

Ordering and concurrency are fundamentally at odds: if message B must
wait for message A, no amount of consumer instances makes B faster.
Systems that pretend otherwise either serialize everything (slow) or
order nothing (wrong). This page says exactly which trades Vulkan
ships, per message key.

## What's guaranteed by default

Messages are appended with strictly increasing ids, and a group's
[claims](/concepts/architecture/) scan the log **in id order** — work is
handed out oldest-first. But
handed out is not finished: with `MessageConcurrency` above 1, multiple
consumer instances, or a retry in the mix, *completion* order is not
guaranteed. The default is full parallelism, honestly labeled.

## Opt-in: one in-flight delivery per key

For messages that carry a [message key](/concepts/message-key/),
`ConcurrencyExclusive` gives you per-key mutual exclusion within a consumer
group:

```go
produced, err := instance.Produce(ctx, &BalanceAdjusted{Account: "acct-42", Delta: -500},
	vulkan.ProduceOptions{
		MessageKey: "acct-42",
		Message:    &vulkan.MessageOptions{Concurrency: vulkan.ConcurrencyExclusive},
	})
```

The guarantee: **at most one delivery per message key is in flight
at a time, per consumer group.** Under the hood it's a
`message_key_lease` row — a same-key message arriving while the key is
busy is recorded [`deferred`](/concepts/lifecycle/) and runs when the
key frees, oldest first; messages with different keys, and messages
with no key, run fully parallel.

Two subtleties keep this from being FIFO. First, exclusivity is the
whole guarantee: a delivery that errors re-enters through the exception
window on its own retry schedule, and the key does not wait — the next
same-key message can run before the failed one's retry. Second, a
message that also enables [compaction](/concepts/message-key/) brings
supersede semantics along: when the key frees, the key's **current
head** runs — the latest version, not every version ever written. If
three updates to `acct-42` land while the first is processing, the
middle one is superseded and only the newest runs. That's "process each
key's current state, one at a time" — exactly right for state-shaped
messages (a user record, a session, a device's latest reading), and
exactly wrong for "apply every delta in sequence."

The hot-key trade comes with it, visibly: a hot key serializes its own
deliveries no matter how many consumer instances you add, and with
compaction enabled same-key produces commit one after another too —
that's what you opted into.

## Opt-in: every message on a key, in order

`ConcurrencyOrdered` is the stricter policy: a keyed message runs only
after every earlier message on its key is resolved for the group, and
the order holds through a failure — the failed message's retry goes
before the messages behind it, and only `dead` releases them. It is
the SQS `MessageGroupId` / Kafka partition guarantee on the message
key, and a different one from exclusive: exclusive answers "one at a
time," ordered answers "don't reorder history." Every row it writes,
what "earlier" means, and what it costs are on
[ordered delivery](/guides/ordered-delivery/).

## Compared to the neighbors

Scored on shipped behavior only — the [Kafka](/compare/kafka/) and
[RabbitMQ & SQS](/compare/rabbitmq-sqs/) pages carry the full
comparisons:

| | Kafka | SQS FIFO | Vulkan today |
| --- | --- | --- | --- |
| Ordering unit | partition (count fixed up front) | MessageGroupId | message key |
| Guarantee | per-partition order | per-group order | per-key order (`ordered`) or exclusivity (`exclusive`); latest version wins when compacted |
| Choose per message? | no — topic topology | yes | yes |
| Unordered fast path on the same topic | no | no — separate queue | yes — messages without a key |

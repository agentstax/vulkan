---
title: Side Effects & Retries
description: What the produce transaction doesn't cover — the email that can't be 'unsent', the ambiguous commit, and the retry loop only you can write.
---

[Transactional produce](/guides/transactional-produce/) makes your
statements and the message one `COMMIT` — both land or neither does.
Two things stay outside that guarantee, and both are yours to handle:
side effects, which are not statements and cannot roll back, and
rerunning the closure, which only you know is safe.

## Side effects don't roll back

Don't call `sendEmailConfirmation()` before the transaction is known
to commit. If a later step fails and rolls back, the database will
undo its half but that email can't be 'unsent'. The transaction covers
your statements and the produced message; a plain function call inside
the closure runs the moment it's reached, and no `ROLLBACK` reaches it.

Here's [the multi-topic closure](/guides/transactional-produce/#several-topics-one-commit)
with an email in the wrong place. Say `orderId` is `4127` and the
customer is `jamie@example.com`:

```go
// ❌ the email fires whether or not the commit happens
err := producer.InTransaction(ctx, ds, func(ctx context.Context, tx producer.Tx) error {
	if _, err := tx.Exec(ctx, `UPDATE orders SET status = 'paid' WHERE id = $1`, orderId); err != nil {
		return err
	}

	sendEmailConfirmation("jamie@example.com") // fires NOW, mid-transaction

	_, err := receipts.ProduceInTx(ctx, tx,
		func(context.Context, producer.Tx, string) (*ReceiptRequested, error) {
			return &ReceiptRequested{OrderId: orderId}, nil
		}, producer.ProduceOptions{})
	return err
})
```

Walk the failure: the produce returns an error (a dropped connection
is enough) -> `InTransaction` rolls back -> order 4127 is unpaid again
and no receipt message exists -> Jamie is holding a "payment received"
email for a payment the database says never happened.

Moving the call below `InTransaction` fixes that, with one catch: it
must sit behind the `nil` check. An error return doesn't confirm the
rollback either — an ambiguous commit failure surfaces as-is (see
[retries](#retries-are-yours-to-own)) — so on error the only safe
move is still no email.

```go
err := producer.InTransaction(ctx, ds, func(ctx context.Context, tx producer.Tx) error {
	// statements and produces only -- everything in here can roll back
	_, err := tx.Exec(ctx, `UPDATE orders SET status = 'paid' WHERE id = $1`, orderId)
	return err
})
if err != nil {
	return err // maybe committed, maybe not -- still no email
}
sendEmailConfirmation("jamie@example.com") // the commit is known here
```

Now walk *this* failure: the process crashes after the commit, before
the send. The payment is recorded, the receipt message flows, the
email never goes out. That's the dual write from the top of
[the produce guide](/guides/transactional-produce/) in the other
order — database first, side effect second — and it has the same fix.
Make the email a message:

```go
_, err := emails.ProduceInTx(ctx, tx,
	func(context.Context, producer.Tx, string) (*EmailRequested, error) {
		return &EmailRequested{To: "jamie@example.com", Template: "payment-received"}, nil
	}, producer.ProduceOptions{})
```

An `email-sender` consumer group calls `sendEmailConfirmation()` in
its [consumerFunc](/guides/consumer-timeouts/) — the relay shape from
the produce guide's external-systems note, pointed at your own mail
provider. The request to send now commits atomically with the payment,
a flaky provider gets retries, and a send that keeps failing is
dead-lettered instead of vanishing with a crashed process.

## Retries are yours to own

`InTransaction` never retries your closure — a transient blip or an
ambiguous commit failure surfaces to you as-is, because only you know
what's safe to rerun. If you wrap your own retry loop around it, make
the rerun dedup-safe by supplying your own idempotency key: unset keys
mint fresh per call, so a naive rerun produces the message twice.

```go
// any stable string works as the key -- here the order id already is one
produced, err := instance.Produce(ctx, &OrderCreated{OrderId: order.Id},
	producer.ProduceOptions{IdempotencyKey: "order-created-" + order.Id})
if err != nil {
	return err
}
if produced.Duplicate {
	fmt.Println("an earlier attempt already landed -- nothing produced twice")
}
```

`Duplicate == true` means an earlier call — or an earlier attempt of
this one, after a commit whose outcome you never learned — already
produced under the same key. The key is an opaque string: one that
parses as a UUID is stored verbatim, anything else is hashed to a
deterministic UUID first, so the same string always lands on the same
claim row. If you mint keys yourself on a hot path, prefer UUIDv7
strings — random-shaped keys cost extra WAL once the claim table is
millions of rows deep. A caller-supplied key also locks that key for
the length of the transaction it runs in, so keep transactions that
reuse keys short.

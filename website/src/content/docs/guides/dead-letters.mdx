Some messages will fail every retry. A malformed payload, a handler
bug, a downstream API that returns 404 for a deleted resource. The question that
separates production-grade messaging from toys is: **where do those
messages go, and how do you get them back?**

In Vulkan, after a message exhausts its retries for a group, its
delivery row flips to `dead` — attempt count and final error on the
row, the payload still in the message log beside it, per consumer
group. Nothing expires behind your back (dead rows live until the
retention drop that removes their log rows), and no separate
dead-letter queue needs provisioning per consumer.

## Triage with the tools you already have

Each topic's tables are named by its id — resolve it once
(`SELECT id FROM topic WHERE name = '...'`; say it returned `1`):

```sql
-- What's dying, and why? Group by error to find the pattern.
SELECT d.last_error, count(*),
       min(m.created_at) AS first_seen, max(m.created_at) AS last_seen
FROM delivery_1 d
JOIN message_log_1 m ON m.id = d.message_id
JOIN consumer_group g ON g.id = d.consumer_group_id
WHERE g.name = 'fraud-screening' AND d.status = 'dead'
GROUP BY 1 ORDER BY 2 DESC;
```

```sql
-- Inspect one casualty in full, with its per-attempt history.
SELECT m.payload, d.attempts, d.last_error,
       l.attempt, l.status, l.error, l.attempted_at
FROM delivery_1 d
JOIN message_log_1 m ON m.id = d.message_id
LEFT JOIN delivery_log_1 l ON (l.consumer_group_id, l.message_id) = (d.consumer_group_id, d.message_id)
WHERE d.status = 'dead'
ORDER BY d.updated_at DESC, l.attempt;
```

This is the underrated payoff of messaging-in-Postgres: dead-letter
triage with `GROUP BY`, joins to your *business tables* ("are all the
dead messages from one merchant?"), and your normal query tooling —
instead of paging through an opaque console one message at a time.

## The recovery loop


1. **Watch.** The dead count per group ships as a metric
   (`vulkan.consumer.exceptions.dead`, via `vulkan metrics list` or the
   Prometheus endpoint on `vulkan manager run --metrics-address`) — or
   it's a `count(*)` threshold on the query above. Wire it into the
   alerting you already have.

2. **Diagnose.** Group dead messages by error; join to business data;
   find the pattern. Usually one bug, many casualties.

3. **Fix and deploy** the handler.

4. **Redrive** — the step that is honestly not shipped yet:

   <ThreadAside label="PROPOSED" title="A redrive verb">
   The proposed shape: reset a group's dead rows to `ready` with a
   fresh attempt budget — all of them, or a subset filtered by error
   text — as a library verb and a CLI command. Today no such verb
   exists, and hand-editing Vulkan's tables is not a supported path.
   Dead rows keep their full record while they wait; the messages they
   point at are retained per the topic's retention policy. The
   cursor-side sibling — rewinding an existing group — is proposed on
   [the replay guide](/guides/replay/).
   </ThreadAside>

5. **Confirm.** The same triage query, trending to zero for new
   traffic once the fixed handler is live.


<ThreadAside label="CAUTION" title="Poison pills don't block the line">
A message that fails forever never blocks the messages behind it —
failed deliveries back off and dead-letter individually, and a `dead`
row doesn't hold back the group's committed cursor. This is the
per-message failure state that log-only systems can't express: in
Kafka, a poison message at offset N means choosing between stalling the
partition at N or skipping data. In Vulkan it means one row in `dead`
and an otherwise unremarkable Tuesday.

</ThreadAside>

## Per-group isolation

Dead-lettering is scoped to the consumer group, because failure is an
opinion of the *consumer*, not a property of the message. The same
message can be `dead` for `fraud-screening` (their API rejected it),
long since processed by `email-receipts` (which wrote no row at all —
success is the [silent path](/concepts/lifecycle/)), and still ahead of
a lagging analytics group — all against one immutable log row. That's
the [fusion](/concepts/queue-and-log/) doing its job.

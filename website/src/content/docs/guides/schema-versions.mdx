---
title: Schema Versions
description: The payload version lives on the message row and is declared by the Message type, so a topic is one name and Register never asks for a version.
---

A message's schema version is a column on its row, written from the Go
type that produced it. A topic is one name with one log; rows of
different versions sit in it side by side, and a consumer group reads
only the rows at its own type's version.

## The type declares its version

```go
type OrderPlacedV2 struct {
	OrderId string `json:"order_id"`
	Total   Money  `json:"total"`
}

func (OrderPlacedV2) SchemaVersion() int { return 2 }

instance, err := client.RegisterProducer[OrderPlacedV2](ctx, "orders.placed", nil)
must(err)
```

`Register` is where a type meets a topic, on both the producer and the
consumer, and it constrains `Message` to `vulkan.Versioned`, one method:
`SchemaVersion()`. Forget it and the program does not compile, which is
the same guarantee the positional parameter gave (no way to bind a type
to a topic without saying which version) moved from a runtime check to
the type checker. The struct name and its version sit two lines apart,
so the `V2` suffix and the `2` are read together. The method is the
only source. There is no config field that overrides it, because two
places to say one fact is how they drift.

`NewClient` takes no type argument. One client registers as many types
as the process emits; the type argument sits on the register call that
names the topic it goes to.

Every produce writes the method's value into the row:

```sql
message_log_<id>.schema_version BIGINT NOT NULL   -- what this row's payload is
```

and `topic_config` loses its `schema_version` column: `UNIQUE (name)`.
One topic, one log, one id space, rows of any version interleaved.

## A group reads its own version and steps over the rest

```go
instance, err := client.RegisterConsumer[OrderPlacedV2](ctx, "fraud-scoring", "orders.placed", nil)
must(err)
```

The claim adds `m.schema_version = $version` beside the binding
predicate it already has. A v1 row under a v2 group is treated the way
a routing key that matches no binding is treated: the cursor passes over
it, nothing decodes it, and the group's lag never counts it. The
exception claim filters the same way, so a v1 row that was dead-lettered
or delayed never replays weeks later into a v2 struct. That replay was
the bug the topic-key design existed to prevent, and it stays
prevented.

A rolling deploy is then two groups on one topic. Say `orders.placed`
has been live a month at v1 with `Total int64` cents and the change is
`Total Money`. Deploy producers built on `OrderPlacedV2` -> new rows
carry `schema_version = 2` -> the existing `fraud-scoring` group on
`OrderPlacedV1` keeps draining v1 rows and steps over v2 -> a second
group `fraud-scoring-v2` on `OrderPlacedV2` does the opposite. When the
v1 group's lag is 0 and no v1 rows remain, stop it. Nothing ever
decoded a v1 row with the v2 struct.

## Compacted topics

Compaction is per key per topic, and the winner compare reads the
version first: `(schema_version, compaction_rank, id)`. A v2 write for
`acct-1` becomes the key's head whatever its rank, and the v1 row stops
being claimable. Inside one version, rank then id decide as before.

That ordering is what makes the bridge pattern work on one topic. A
group bound to the old type consumes each key's current head and
re-produces it as the new type at `CompactionRank -1`. Being v2, the
copy beats the v1 head it was made from; being rank -1, it loses to any
live rank-0 v2 write for the same key, in either arrival order.
`examples/phase_1/schemaevolutionlab` runs that end to end, including
a crash mid-drain.

Retirement is a query, not a guess. `client.Topic("orders.placed").Health` lists
every version present in the log with the compaction heads still at it
and each group's unread rows at it; zero of both is the verdict. A
version with heads at it reads "compaction heads remain" no matter how
drained the groups are.

## What it costs

- A v1 row lives until retention drains it, not until you drop its
  family. Retiring v1 is "no v1 rows or heads remain", not `DROP TABLE`.
- Partitions and retention are shared across versions. A version cannot
  be sized or retained on its own.
- Eight bytes per row.
- `GetTopic`, `DestroyTopic`, `RenameTopic` and the CLI take a name only;
  there is no `--schema-version` flag anywhere.

## Not shipped

Reading an older version through a converter (Confluent's reader
schema, Temporal's data converter) instead of skipping it is a separate
piece of work; the skip predicate is where it would plug in. It waits
until the skip has been lived with.

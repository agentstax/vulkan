Replay is the feature that quietly changes how you build. When history
is retained and cursors are cheap, "reprocess everything since Tuesday"
stops being a war-room project. This page is honest about which half of
that ships today.

<ThreadAside label="NOTE" title="Partly shipped, partly proposed">
Reading history with a **new** consumer group works today — it's the
default. Rewinding an **existing** group is a proposed capability; the
sections below marked *proposed* are the spec for it, not shipped API.

</ThreadAside>

## Shipped today: bootstrap a new service from history

Your team ships a search service eight months after orders started
flowing. With a consumed-and-gone queue, you'd write a custom backfill
against the orders table, keep it consistent with live traffic, and
pray during the cutover. In Vulkan, a newly registered group's cursor
starts at zero — it reads everything retention still holds:

```go
indexer, err := searchConsumer.Register(ctx, "search-indexer",
	registered.Name, topic.SchemaVersion(1), nil)
must(err)
must(indexer.Consume(ctx, indexOrder))
```

The group chews through history at its own pace (its lag shrinking is
your progress bar) and seamlessly arrives at live traffic. Other groups
never notice it happened.

This also gives you a shipped — if blunt — recovery tool: a handler bug
that corrupted a projection can be fixed by pointing a **fresh group**
with the corrected handler at the topic and rebuilding the projection
from scratch, then retiring the old group.

## Proposed: rewind an existing group

Tuesday 09:14: a deploy ships a bug in `warehouse-sync` that silently
mis-handles EU orders. Wednesday: you notice. The proposed loop:


1. Deploy the corrected handler.

2. Rewind the group to before the damage — the proposed verb takes a
   message id or a timestamp and moves the group's cursor back:

   ```go
   // PROPOSED — not shipped API.
   err := messageAdmin.RewindGroup(ctx, "warehouse-sync", registered.Name,
       topic.SchemaVersion(1), admin.RewindTo{Timestamp: tuesdayMorning})
   ```

3. Watch it re-run the window. Handlers are idempotent (they already
   had to be — [at-least-once delivery](/concepts/lifecycle/)), so
   re-processing messages it had handled correctly is harmless.


Spec questions the proposal has to answer before it ships — recorded
here so the eventual design is reviewable against them:

- **Delivery rows in the window.** A rewind re-runs messages that may
  have open or `dead` delivery rows; the verb must define whether those
  reset, keep their attempt history, or block the rewind.
- **Safety rail.** Rewinding a group that fires emails is exciting in
  the wrong way — the verb should report what it *would* redeliver
  (count, id range, time span) before doing it.
- **Retention interplay.** A rewind target older than retention is an
  error naming the oldest retained message, not a silent partial
  replay.

## What replay costs

Nothing at write time — it's the same append-only log either way. At
read time it's sequential indexed reads, the cheapest thing Postgres
does. The real budget question is **retention**: how much history to
keep, set per topic at registration:

```go
registered, err := messageAdmin.RegisterTopic(ctx, "orders",
	topic.SchemaVersion(1), &topiccontroller.TopicConfig{
		RetentionTTL: 30 * 24 * time.Hour,
	})
```

The default keeps everything forever; a TTL trades replayable history
against storage. Remember the default safety:
[retention never drops past the slowest group's cursor](/concepts/fan-out/)
unless the topic opts into `AllowDropPastCommitted`.

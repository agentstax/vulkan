One client wraps the pool and holds the ambient config. Every resource is
named from it as a handle (`client.Topic[OrderPlaced]("orders")`,
`client.Topic[OrderPlaced]("orders").Group("billing")`), and the verbs
live on the thing they act on. Before it, the same
program needed `NewConsumer`, `NewProducer`, `NewScheduler`,
`NewMessageAdmin`, and `NewSystemManager`, each with its own config
carrying its own `Logger` and `Retry`. The group-config half of this,
what is stored and how instances read it back, has its own page:
[consumer group config](/guides/consumer-group-config/).

## Two grammars

The client selects the noun: `Topic[T](name)`, `Scheduler(name)`, and a
topic handle selects its own: `Group(name)`, `Key(messageKey)`,
`Producer()`. A handle uses the bare verb: `orders.Register`,
`orders.Destroy`, `nightly.Suspend`. It already knows what it is, and
`orders.DestroyTopic` says topic twice. A plural method reads the materialized
collection: `Topics`, `Schedulers`. The act verbs on typed instances
(`Consume`, `Produce`, `Schedule`) follow the same split.

## The type argument

The topic carries the message type and everything under it inherits
it. `client.Topic[OrderPlaced]("orders")` is spelled once, and the
group's `Register`, the producer's `Register`, and the key reads take
no type of their own. Go cannot infer a type from a string, so the
argument is always written, and a wrong type on a consumer becomes
impossible to spell: the handler's parameter type is the topic's.

The admin verbs never look at it. `Register`, `Destroy`, `Migrate`,
`Rename`, `Health`, and `Metrics` run the same for any type, so a
topic holding two schema versions is two handles on the same rows:
`Topic[OrderPlacedV1]` reads V1 payloads, `Topic[OrderPlacedV2]` reads
V2, and either one destroys the topic.

A caller that does not know the type, the CLI and any admin-only
script, uses `vulkan.RawPayload`: the stored JSON bytes as they are,
declaring version `0`. It works on every admin and key read. A consumer
cannot register with it and a produce with it is refused, so no row is
ever stored or read at version 0.

```go
// an operator script -- no message type in scope
orders := client.Topic[vulkan.RawPayload]("orders")
health, err := orders.Health(ctx)
head, err := orders.Key("order-42").CompactionHead(ctx) // head.Message is the raw JSON
```

The schedule is the one handle outside the tree. Its `Register` takes
the payload value, and Go infers the type from that argument, so no
type is written there either.

## Connect

```go
ctx, stop := vulkan.LifecycleContext(nil)
defer stop()

pool, err := vulkan.NewPostgresPool(ctx, "app_user", os.Getenv("PGPASSWORD"), "localhost", "app_db", nil)
if err != nil {
	return err
}
defer pool.Close()

client, err := vulkan.NewClient(ctx, pool, &vulkan.ClientConfig{
	AllowDestroy: false,
	Logger:       logger,
})
if err != nil {
	return err
}
```

`NewClient` dials the pool once before it returns, so a wrong address
or credential fails there rather than at the first produce. The pool
stays yours: `client.InTransaction` and raw access keep their seam, and
the app that opened the pool closes it. `ClientConfig` is the ambient
set held once: `Schema`, `Logger`, `Retry` (the client's own Postgres
retry curve, never a message's), and `AllowDestroy`. Every config below
inherits them and so none of them carries a `Logger` or `Retry` field.
That removed the worst trap on the old `ConsumerConfig`: `Retry` next
to `Message.Retry`, both `*RetryPolicy`, one for the Postgres calls and
one for redelivery.

A first program imports `vulkan` and nothing else of ours. Every type a user
spells lives in `vulkan`: `ConsumerConfig`, `ConsumeOptions`,
`ProducerConfig`, `ProduceOptions`, `ScheduleConfig`,
`TopicConfig`, `DestroyOptions`, `MessageOptions`, `RetryPolicy`, `Tx`,
`RawPayload`, `MetaFromContext`, `Terminal`, `Delay`. A consumer's first program used to import
`topiccontroller` for `TopicConfig` and `schedulecontroller` for
`ScheduleConfig`; "controller" is the library's word for its
persistence layer and a user should never have to type it.

## Building the pool

`NewPostgresPool` takes the DSN exploded in the order the URL writes
it, `postgres://user:password@host:port/database`, and the config holds
what is optional after that:

```go
pool, err := vulkan.NewPostgresPool(ctx, "app_user", os.Getenv("PGPASSWORD"), "localhost", "app_db",
	&vulkan.PostgresConnectionConfig{MaxConns: 20})
```

The password goes inline, `""` meaning no password, which is real on a
trust or peer auth setup. `PostgresConnectionConfig` carries `Port`,
`MaxConns`, `ConnectTimeout`, `TLSConfig`. `Schema` is not among them,
since it was never a connection fact — it sits on `ClientConfig`.

It builds the pool and does not dial; `NewClient` is what pings it. So
a wrong password surfaces at `NewClient`, not here.

A caller who already holds a DSN skips it entirely —
`pgxpool.New(ctx, dsn)` and hand the result to `NewClient`, which takes
any `*pgxpool.Pool`. That is the path for a `DATABASE_URL` deployment,
and for an application whose pool already exists before Vulkan enters
it.

Whichever way the pool is built, you close it. Vulkan never does, and
the client has no `Close` — `defer pool.Close()` is the only shutdown
this layer needs.

Taking a pool commits the public API to pgx. The commitment was already
there: `vulkan.Tx` hands your closure pgx's own result types. A team
standardized on `database/sql` still runs one pool for the whole
application — build the pgxpool, hand it to Vulkan, and derive the
`*sql.DB` view with pgx's own `stdlib.OpenDBFromPool(pool)`, which
shares that pool instead of opening a second one and leaves closing to
you. The derivation runs only that direction, since an arbitrary
`*sql.DB` cannot produce a pgxpool. The cost lands on a team that will
not import pgx at all: there is no handoff for them, and they run a
second pool beside Vulkan's.

A pool you built can carry its own `search_path`, set on the DSN as
`?search_path=myapp` or in an `AfterConnect` hook, and Vulkan does not
care: every statement it runs names its schema outright and the pool
sets no path of its own (below).

## The schema

Vulkan's tables live in one Postgres schema, `vulkan` unless you say
otherwise:

```go
client, err := vulkan.NewClient(ctx, pool, &vulkan.ClientConfig{Schema: "payments"})
```

One schema is one installation. Two clients on two schemas in the same
database each get their own catalog, their own topics, their own
sequences, and neither can read the other's rows — `orders` registers
in both and they are different topics. `client.System().Register` creates the
schema if it is missing, which needs CREATE on the database; without
that you get [VK0064](/errors/VK0064/), and the fix is to create the
schema yourself and grant the role USAGE and CREATE on it.

The pool sets no `search_path`. Every statement Vulkan runs names its
schema outright, `vulkan.message_log_4` and never `message_log_4`, so
the connection keeps whatever default it came with. Your own SQL inside
`InTransaction` then resolves the way it would on any other connection:
a `CREATE TABLE orders` in that closure lands in your default schema,
not in Vulkan's.

The diagnose queries on every error page carry a `{schema}` placeholder
because a psql session has no reason to have Vulkan's schema on its
path. Paste one unfilled and an unqualified `message_log_4` resolves to
nothing, which reads as the row being gone rather than the query
looking in the wrong place.

## Consume

```go
payments, err := client.Topic[PaymentRequestedV1]("payments.requested").Group("charge-cards").Register(ctx,
	&vulkan.ConsumerConfig{
		Message: &vulkan.MessageOptions{
			Timeout: 10 * time.Second,
			Retry:   &vulkan.RetryPolicy{MaxRetries: 3, BaseDelay: 2 * time.Second},
		},
	})
if err != nil {
	return err
}

return payments.Consume(ctx, func(ctx context.Context, payment *PaymentRequestedV1) error {
	fmt.Printf("charging %s\n", payment.OrderId)
	return nil
}, &vulkan.ConsumeOptions{BatchLimit: 20})
```

`ConsumerConfig` is the group's meaning and is stored on the group's
rows: `Message`, `MessageMin`/`MessageMax`, `ConcurrencyOverride`,
`Start`, `Bindings`, `ExceptionInitialBackoff`, `MaxRangeReclaims`.
`ConsumeOptions` is how this one session runs: `BatchLimit`,
`QueueSize`, `MessageConcurrency`, the poll rate and margins, the
shutdown budget. A bigger box runs a bigger batch and nothing durable
changes. Which field goes where, and what happens when two replicas
disagree, is the
[group config page](/guides/consumer-group-config/).

## What a declaration does

Newest wins, every time. A differing declaration overwrites the stored
document and logs [VK0059](/errors/VK0059/) naming the change as
`old -> new`; an identical one writes nothing. `Start` and `Bindings`
keep their own rules: read once at creation, and install / wait.

That is right for a rolling deploy and wrong for two services that both
think they own `charge-cards` — they overwrite each other forever, and
the tell is the same VK0059 line on every restart of either one. One
declaring service per group is a convention, not a constraint.

There is no strict form. A refusing one was built and reverted: a
service that refuses a differing config can never have its config
changed without first redeploying it as accepting, and nobody wants
that dance.

<ThreadAside label="PROPOSED" title="Reading the outcome back">
The log makes an overwrite visible and a log line is not an API, so a
typed instance would say what its own declaration did — created, joined,
or updated, the way bindings already report installed / joined /
waiting. Not built.

</ThreadAside>

## Produce

```go
requests, err := client.Topic[PaymentRequestedV1]("payments.requested").Producer().Register(ctx,
	&vulkan.ProducerConfig{
		Message: &vulkan.MessageOptions{Timeout: 10 * time.Second},
	})
if err != nil {
	return err
}

produced, err := requests.Produce(ctx, &PaymentRequestedV1{OrderId: "order-812"}, nil)
```

`nil` options means the defaults, on `Produce` and `Consume` alike -- one
rule for every optional parameter. `ProducerConfig` declares nothing durable
(a producer has no row of its own) and is just this process's message
defaults and batching.

## Schedule

A schedule is a declaration that returns a runnable `SchedulerInstance`;
the `Scheduler` handle administers its stored row.

```go
nightly, err := client.Scheduler("nightly-report").Register(ctx,
	"reports.requested", "0 3 * * *",
	&ReportRequestedV1{Kind: "nightly"}, &vulkan.ScheduleConfig{
		Timeout:     time.Minute,
		Concurrency: vulkan.ConcurrencyExclusive,
	})
if err != nil {
	return err
}

return nightly.Schedule(ctx)
```

`SchedulerInstance.Schedule` runs the system manager. The schedule producer is a
fleet worker and it produces every registered schedule, not just this one,
so the verb's name is a bit deceptive: a program that calls
`nightly.Schedule` is running every worker in the fleet without having
said so. `Consume` does the same thing, which is what makes the
symmetry honest — a user who has learned `Register` then `Consume` and
`Register` then `Produce` gets `Register` then `Schedule` and nothing
new, and none of the three is quietly doing more than the others. The
alternative weighed against it was a handle with no run verb and
`client.Manager().Run` as the only way to make a schedule fire. A program
that registers a schedule and exits has registered one that never
fires until something in the deployment runs a manager — which any
consumer does.

The schedule name sits on `SchedulerHandle`, so it cannot trade places with
the target topic in `Register`. The schedule stays outside the typed tree
on purpose: only `Register` knows a payload type, and every other verb on
it is keyed by the schedule's name alone, so a topic on the handle would
be a redundant argument on seven of eight verbs and would put a topic on
every `vulkan schedule` command. A schedule's redeclaration warns
[VK0062](/errors/VK0062/), the consumer's sibling.

## Handles

`client.Topic[PaymentRequestedV1]("payments.requested")` does no I/O and
cannot fail. It is a name plus the client, and every verb on it resolves
the name when called:

```go
orders := client.Topic[PaymentRequestedV1]("payments.requested")
topic, err := orders.Get(ctx) // *vulkan.Topic; (nil, nil) when not registered
renamed, err := orders.Rename(ctx, "payments.card-requested")
err = orders.Destroy(ctx, nil) // vulkan.ErrTopicNotFound if it is gone
```

`Get` is the snapshot read and the only comma-ok verb. Every other verb
returns the not-found error itself. Any name-keyed API works this way:
`Destroy` is one statement whose zero-rows-affected is the existence
check, atomically, and a `Get` before it would only add a window in
which the answer can change. `kubectl delete`, `sqs.DeleteQueue`, and
JetStream's `stream.DeleteConsumer(ctx, name)` are the same shape.

Two honest notes. JetStream's own `js.Stream(ctx, name)` is the other
design: it fetches the stream's info, returns not-found at
acquisition, and caches the row on the handle, which is why it then
needs both `CachedInfo()` and `Info(ctx)`. Pub/Sub's
`client.Subscription(id)` is the no-I/O design this page copies. Both
are legitimate; the no-I/O one was picked so a handle can never hold a
row that has gone stale and so a one-shot CLI verb is one round trip.
And a `client.GetSchedule(ctx, name)` returning the handle with its
row as sugar over `Scheduler(name).Get(ctx)` would fit; it was left out
to keep one read path, and I'm not sure that is the right call for
scripts.

## Admin, resource by resource

Every block reads the same way: list the collection, name one, read
it, act on it.

```go
// plural reads materialized values; singular selectors return handles
topics, err := client.Topics(ctx)
orders := client.Topic[ReadingV1]("device.readings")
topic, err := orders.Get(ctx)
if err != nil {
	return err
}
if topic == nil {
	topic, err = orders.Register(ctx, nil)
	...
}
err = orders.Migrate(ctx, 3)
health, err := orders.Health(ctx)
renamed, err := orders.Rename(ctx, "payments.card-requested")
err = orders.Destroy(ctx, nil) // refused unless ClientConfig.AllowDestroy
heads, err := orders.CompactionHeads(ctx)

// a message key hangs off its topic
device := orders.Key("device-7")
current, err := device.CompactionHead(ctx) // vulkan.ErrCompactionHeadNotFound when nothing is under the key
versions, err := device.Messages(ctx, 20)

// groups hang off their topic
groups, err := orders.Groups(ctx)
group := orders.Group("charge-cards")
registeredGroup, err := group.Get(ctx)
workers, err := group.Workers(ctx)
err = group.Destroy(ctx, nil)
dead, err := group.ListDeadMessages(ctx, 50) // proposed verbs land here
err = group.Rewind(ctx, vulkan.AtTime(t))    // proposed

// schedules
schedules, err := client.Schedulers(ctx)
nightly := client.Scheduler("nightly-report")
schedule, err := nightly.Get(ctx)
err = nightly.Suspend(ctx)
err = nightly.Unsuspend(ctx)
result, err := nightly.Run(ctx, nil)
status, err := nightly.Status(ctx)
messages, err := nightly.Messages(ctx, 20)
err = nightly.Destroy(ctx)

// system -- the same handle grammar; today it takes no name
sys := client.System()
system, err := sys.Get(ctx)
err = sys.Register(ctx, nil)
err = sys.Migrate(ctx, 5)
err = sys.Destroy(ctx, nil)

// system-owned collections and their singular handles
alerts, err := sys.Alerts(ctx)
currentAlert, err := sys.Alert("partition_count:orders").Get(ctx)
```

A plural noun lists materialized resources: `client.Topics`,
`orders.Groups`, `client.Schedulers`, `sys.Alerts`.
Its singular noun returns a no-I/O handle. Terminal reports and retained
history keep the verb that says what they return: `Health`, `Status`,
`Workers`, and `Messages`. A group's binding set is a handle
under the group, `orders.Group("charge-cards").Binding().Get(ctx)`, nil
when the group never declared one.

A message key is a handle under its topic. `orders.Key("device-7")`
names it, `CompactionHead` reads the key's winning message and returns
[VK0066](/errors/VK0066/) when no compacted message was produced under
it, and `Messages` reads the retained history newest first. The key is
a message property with two readers, compaction and the concurrency
policy, which is why the handle is named for the key: the lease facts
belong on the same handle when they get a read. The head used to be read inside a transaction on the producer
instance and outside one on a separate `CompactionController` keyed by
topic id, two objects for one fact. `orders.CompactionHeads` lists
every key's head on the topic, all of them: a topic can hold a million
keys, and a limit without a cursor would only be a peek, so paging is
left until a workload asks for it.

The system is a singleton and a handle anyway — one schema is one
installation, so there is only ever one row to name. The day that
changes the API grows by one parameter: `client.System(name).Register(ctx,
cfg)`, topics nesting under it as
`client.System(name).Topic(name)` the way groups nest under topics, and
`client.Topic[T](name)` staying as the default system's shortcut. The
verbs that own system state already sit there: `Register`, `MigrateTopics`,
`Bindings`, and `Alerts`. The manager is its
own `client.Manager()` handle because it is a running subsystem.

## Metrics

<ThreadAside label="PROPOSED" title="Metrics as resources">
Metrics split live state from collected history. `Snapshot(ctx)` asks the
source tables what is true now. `Latest(ctx)` and `History(ctx, limit)` read
observations already written to `__system.metrics`.

The first pass puts metrics handles on the system, a topic, and a consumer
group:

```go
systemMetrics := client.System().Metrics()
definitions := systemMetrics.Definitions() // []vulkan.MetricDefinition; no I/O
latest, err := systemMetrics.Latest(ctx)    // []*vulkan.Measurement

topicMetrics := client.Topic[PaymentRequestedV1]("payments.requested").Metrics()
topicSnapshot, err := topicMetrics.Snapshot(ctx) // *vulkan.TopicSnapshot; live

groupMetrics := client.Topic[PaymentRequestedV1]("payments.requested").
	Group("charge-cards").Metrics()
groupSnapshot, err := groupMetrics.Snapshot(ctx) // *vulkan.ConsumerGroupSnapshot; live

backlog := groupMetrics.CursorBacklog()  // *vulkan.MetricHandle; no I/O
point, err := backlog.Latest(ctx)        // *vulkan.Measurement
history, err := backlog.History(ctx, 20) // []*vulkan.Measurement; newest first
```

`System().Metrics().Latest(ctx)` returns the newest retained point for every
series actually published, ordered by name and then its sorted attributes. That
includes Vulkan built-ins and user-produced metrics. It says what exists in
storage, where `Definitions()` says what Vulkan knows how to produce before
anything has been collected.

A definition is metadata, never a value:

```go
type MetricDefinition struct {
	Code          string
	Name          string
	Kind          MetricKind
	Unit          MetricUnit
	Description   string
	Scope         MetricScope
	AttributeKeys []string
}
```

`System().Metrics().Definitions()` returns every Vulkan built-in definition,
ordered by VK code, including consumer-session definitions whose instance
handle is later work. `Topic().Metrics().Definitions()` returns topic-scoped
definitions. `Group().Metrics().Definitions()` returns consumer-group-scoped
definitions. All three are in-memory reads over the same catalog used by the
collector, `vulkan explain`, and Prometheus `HELP`; they never touch Postgres.
Custom user definitions are later work, so an observed user metric appears in
`Latest` but not `Definitions`.

The scopes and their required attributes are fixed:

| scope | required attributes |
| --- | --- |
| `MetricScopeSystem` | none, except alert-check series require `alert` |
| `MetricScopeTopic` | `topic` |
| `MetricScopeConsumerGroup` | `topic`, `group` |
| `MetricScopeConsumerSession` | `topic`, `group`, `version`, `session` |

Built-ins are selected as methods, so a caller can find them from the handle
without copying a wire name:

```go
// system levels
systemMetrics.UnclaimedWorkers()
systemMetrics.OldestUnclaimedAge()
systemMetrics.FailingWorkers()
systemMetrics.OverdueSchedules()
systemMetrics.OldestDueAge()
systemMetrics.SuspendedSchedules()
systemMetrics.ActiveAlerts()
systemMetrics.ResolvedAlerts()

// one built-in alert check; alert becomes the series' `alert` attribute
systemMetrics.CheckTopicsEvaluated("partition_count")
systemMetrics.CheckTopicsFailed("partition_count")
systemMetrics.CheckPublishedAlerts("partition_count")
systemMetrics.CheckResolvedAlerts("partition_count")

// topic level
topicMetrics.Compacted()

// consumer-group levels
groupMetrics.CursorHead()
groupMetrics.CursorClaimed()
groupMetrics.CursorCommitted()
groupMetrics.CursorBacklog()
groupMetrics.CursorInflight()
groupMetrics.ReadyExceptions()
groupMetrics.InflightExceptions()
groupMetrics.DeferredExceptions()
groupMetrics.DeadExceptions()
groupMetrics.OldestUnresolvedAge()
groupMetrics.OpenLeases()
groupMetrics.AbandonedRoutinesOutstanding()
groupMetrics.AbandonedRoutinesTotal()
groupMetrics.AbandonedRoutinesSelfClearLatencyAverage()
```

Every selector returns the same `MetricHandle` shape. The topic and group names
on the resource handles supply their attributes. A selector does not query the
resource and does not hold its row.

The system handle carries the one string escape hatch. It is how a caller reads
a user-produced series, a Vulkan series selected dynamically from a definition,
or a consumer-session series before instance metrics handles exist:

```go
metric := systemMetrics.Metric(
	"checkout.request.duration",
	map[string]string{"region": "us-east-1", "result": "approved"},
)
point, err := metric.Latest(ctx)
history, err := metric.History(ctx, 20)
```

It accepts a name and the exact attribute set because arbitrary names have no
Topic or Group semantics. `Topic().Metrics()` and `Group().Metrics()` expose
only their typed built-ins.

`Latest` returns `(nil, nil)` when the exact series has no retained point.
`History` requires a positive limit and returns an empty slice for the same
absence. Those reads do not prove that the named topic or group exists: a
collected series can outlive its resource, and a new resource may exist before
the collector reaches it. `Snapshot` is the live existence check and returns
`ErrTopicNotFound` or `ErrGroupNotFound`.

The observation time stays on every returned value. For example,
`payments.requested` is topic id `41`, `charge-cards` is group id `73`, and
`__system.metrics` is topic id `9`. The collector writes backlog `27` at
10:03. Work finishes before the next collection, so at 10:07 the two reads can
honestly disagree:

```go
live, err := groupMetrics.Snapshot(ctx)
// live.Cursor.Backlog == 19                 -- source tables at 10:07

collected, err := groupMetrics.CursorBacklog().Latest(ctx)
// collected.Value == 27
// collected.At    == 2026-09-05T10:03:00Z  -- newest retained observation
```

`Latest` means newest retained, not fresh. A caller with a freshness requirement
compares `Measurement.At` to its own threshold; the library does not silently
turn an old collected value into live state.

</ThreadAside>

## The manager

```go
return client.Manager().Run(ctx)
```

Most deployments never call this. `Consume` runs the system manager
beside the session, so a process with one live consumer already keeps
the fleet-wide workers running — the topic janitor, the schedule
producer, the metrics collector, the built-in checks — for every topic
in the deployment, not just its own. `ManagerHandle.Run` is for the process
with no consumer to hang upkeep on: `vulkan manager run`, or a service
that wants to carry it explicitly.

Nothing is refused. Every `Consume`, `ManagerHandle.Run`, and
`SchedulerInstance.Schedule` call
in the fleet starts its own reconcile loop, and they all try to claim
the same row: `manager` under the system's owner, declared
`target_instances = 1`. One claim wins, the losers retry every 30
seconds and take over within that window when the holder stops. It is
the gate the group's own workers already run under, pointed at the
manager itself.

That column is the deployment's dial and it takes effect with no
deploy:

| `target_instances` | what runs |
| --- | --- |
| `0` | nothing, everywhere — the loop logs [VK0035](/errors/VK0035/) and reconciles no rows |
| `1` | one process reconciles, the rest wait. The default. |
| `N` | N processes reconcile |
| `-1` | every process reconciles, no cap |

`ClientConfig.DisableManager` is the per-process opt-out. Two
deployments need it: consumer pods beside a dedicated `vulkan manager
run`, and consumers under a database role with no DDL rights, since
the topic janitor creates and drops partitions.

Admin verbs run nothing. The producer runs nothing, and that is the
one gap: a deployment that only produces accumulates partitions with
no log line saying why.

The `worker_liveness` alert closes it, the third built-in beside
`partition_count` and `compaction_read_cost`. Its condition is the
state the fleet already classifies: a worker row that wants instances
and has none live. Nothing is running it.

It reports the way both other built-ins do, once at register and once
on a schedule:

- `ProducerHandle.Register` logs [VK0063](/errors/VK0063/) naming the topic,
  the unclaimed rows, and who declared them. The pass reads only:
  nothing is published, and `Register` never fails on it.
- Hourly under the manager, the check publishes an active alert to
  `__system.alerts` and resolves it once the rows are claimed again.
  `vulkan alert list` reads both states.

Worked case: `orders-api` runs only `client.Topic[OrderPlaced]("orders.placed").Producer().Register`.
Its register-time line names
`orders.placed (topic_janitor)`, so nothing is dropping that topic's
expired partitions. `fulfillment` starts its `Consume` on the
`pack-orders` group, its manager claims that row, and the next
`orders-api` restart is silent. Scale `fulfillment` to zero later and
the hourly check publishes the group itself:
`pack-orders (message_consumer, exception_consumer, cursor_advancer, manager)`.

One process that produces and then consumes trips the register-time
line once on a cold start, because `Register` runs before `Consume`
claims anything. An instance row lingers 30 seconds past its last
heartbeat, so a restart inside that window finds the old rows still
live and says nothing; a longer gap logs one line and clears itself.

## Testing your code

The library returns concrete `ProducerInstance[T]`, `ConsumerInstance[T]`,
and `SchedulerInstance[T]` values. A package that needs a fake declares the
small interface it consumes beside its own code; Vulkan does not publish a
second, partial definition of those instances. The client stays concrete for
integration tests.

## Names

The suffix says what a value does. A handle is the lazy identity plus
client (`TopicHandle`, `GroupHandle`, `KeyHandle`, `SchedulerHandle`); the bare noun is
the materialized domain value returned by `Get` (`Topic`, `Group`,
`Schedule`). `StoredMessage[T]`, `Alert`, and `Measurement` follow the same rule:
they are values, not handles. JSON is unaffected; wire names live in field
tags.

The rest of the public grammar follows the value's role: `Config` for
declarations, `Options` and `Item` for command inputs, `Result` for command
outputs, `Snapshot` for point-in-time observability, `Status` for current
state, `Summary` for an aggregate projection, `Health` for a verdict,
`Declaration` for a declared relationship, `Row` for a table-exact scan, and
`Instance` for running process state. A projection includes its subject when
the bare role would be vague: `ScheduleGroupSummary`,
`ScheduleMessageStatus`, `TopicVersionHealth`, and
`ConsumerGroupSchemaVersionLag`.

`Data` and `Info` are not roles, so neither is a public suffix. `TopicData`
does not say whether it is a row, snapshot, configuration, or handle;
`Topic` says it is the domain value while its package and return site provide
the context. Datastore scan structs keep `Row` and name the
table they scan: `TopicConfigRow`, `WorkerConfigRow`, `ScheduleConfigRow`.

## Worked case

`charge-cards` runs three replicas on `payments.requested` (topic id
`1`) with the default retry budget. A fourth service, `reconciliation`,
also consumes the group by mistake and declares `MaxRetries: 5`. Its
`GroupHandle.Register` overwrites the stored document, its logger warns
[VK0059](/errors/VK0059/) with the `metadata` change as `old -> new`,
and the three replicas pick the new budget up on their next config
refresh. When the owning service next restarts it declares the default
again -> VK0059 again, the other way round -> and the budget flips on
every deploy of either service until someone reads the warn. Once `reconciliation` stops
declaring the group, the owning service redeclares `MaxRetries: 5`
deliberately and the row shows it:

```sql
SELECT w.name, w.metadata
FROM vulkan.worker_config w
JOIN vulkan.consumer_group_config g ON g.id = w.consumer_group_id
WHERE g.name = 'charge-cards';
--  name             | metadata
--  message_consumer | {"message": {"timeout": "10s", "retry": {"max_retries": 5}}, ...}
```

An operator checking the group from a script needs one round trip, and
no message type:

```go
data, err := client.Topic[vulkan.RawPayload]("payments.requested").Group("charge-cards").Get(ctx)
```

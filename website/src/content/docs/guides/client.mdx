import ThreadAside from '../../../components/thread-aside/thread-aside.svelte';

One client wraps the datastore and holds the ambient config. Every
resource is either registered on it (`RegisterConsumer`,
`RegisterTopic`) or named from it as a handle (`client.Topic("orders")`),
and the verbs live on the thing they act on. Today the same program
needs `NewConsumer`, `NewProducer`, `NewScheduler`, `NewMessageAdmin`,
and `NewSystemManager`, each with its own config carrying its own
`Logger` and `Retry`; this page collapses those into `vulkan.NewClient`.

<ThreadAside label="PROPOSED" title="This page is the spec">
Nothing on this page is shipped API. Every sample is what the code
would look like once built; the mapping table near the end says where
each shipped verb goes. The group-config half of it, what is stored and
how instances read it back, has its own page:
[consumer group config](/guides/consumer-group-config/).

</ThreadAside>

## Two grammars

The client names the noun: `RegisterTopic`, `ListTopics`, `Topic(name)`.
It spans every resource so the noun has to be in the method. A handle
uses the bare verb: `orders.Rename`, `orders.Destroy`, `nightly.Suspend`.
It already knows what it is, and `orders.DestroyTopic` says topic twice.
The act verbs on typed instances (`Consume`, `Produce`) are handle verbs
too. JetStream, Temporal, and Pub/Sub all land on this split; a user
coming from any of them has nothing new to learn here.

## Connect

```go
// PROPOSED — not shipped API.
ctx, stop := vulkan.LifecycleContext(nil)
defer stop()

ds, err := datastore.NewPostgresDatastore(ctx, "example_user", "localhost", "example_db",
	&datastore.PostgresConnectionConfig{Pass: "example_password"})
if err != nil {
	return err
}
defer ds.Close()

client, err := vulkan.NewClient(ds, &vulkan.ClientConfig{
	AllowDestroy: false,
	Logger:       logger,
})
if err != nil {
	return err
}
```

The client wraps `ds`, it does not connect. The pool stays yours:
`producer.InTransaction` and raw access keep their seam, and the app
that opened the pool closes it. `ClientConfig` is the ambient set held
once: `Logger`, `Retry` (the client's own Postgres retry curve, never a
message's), and `AllowDestroy`. Every config below inherits them and so
none of them carries a `Logger` or `Retry` field. That also removes the
worst trap on today's `ConsumerConfig`: `Retry` next to `Message.Retry`,
both `*RetryPolicy`, one for the datastore and one for redelivery.

A first program imports `datastore` and `vulkan`. Every type a user
spells lives in `vulkan`: `ConsumerConfig`, `ConsumeOptions`,
`ProducerConfig`, `ProduceOptions`, `ScheduleSpec`, `ScheduleConfig`,
`TopicConfig`, `DestroyOptions`, `MessageOptions`, `RetryPolicy`, `Tx`,
`MetaFromContext`, `Terminal`, `Delay`. Today a consumer's first program
imports `topiccontroller` for `TopicConfig` and `schedulecontroller`
for `ScheduleConfig`; "controller" is the library's word for its
persistence layer and a user should never have to type it.

## Consume

```go
// PROPOSED — not shipped API.
payments, err := client.RegisterConsumer[PaymentRequestedV1](ctx, "charge-cards", "payments.requested",
	&vulkan.ConsumerConfig{
		Message: &vulkan.MessageOptions{
			Timeout: 10 * time.Second,
			Retry:   &vulkan.RetryPolicy{MaxRetries: 3, BaseDelay: 2 * time.Second},
		},
	})
if err != nil {
	return err
}

return payments.Consume(ctx, func(ctx context.Context, payment *PaymentRequestedV1) error {
	fmt.Printf("charging %s\n", payment.OrderId)
	return nil
}, &vulkan.ConsumeOptions{BatchLimit: 20})
```

`ConsumerConfig` is the group's meaning and is stored on the group's
rows: `Message`, `MessageMin`/`MessageMax`, `ConcurrencyOverride`,
`Start`, `Bindings`, `ExceptionInitialBackoff`, `MaxRangeReclaims`.
`ConsumeOptions` is how this one session runs: `BatchLimit`,
`QueueSize`, `MessageConcurrency`, the poll rate and margins, the
shutdown budget. A bigger box runs a bigger batch and nothing durable
changes. Which field goes where, and what happens when two replicas
disagree, is the
[group config page](/guides/consumer-group-config/).

## What a declaration reports

Newest-wins on every restart is right for a rolling deploy and wrong
for two services that both think they own `charge-cards`; they overwrite
each other forever, visibly in the log, and a log line is not an API.
So the instance says what its declaration did, the same way bindings
already report installed / joined / waiting:

```go
// PROPOSED — not shipped API.
switch payments.Declaration {
case vulkan.DeclarationCreated: // first declaration, the row was created
case vulkan.DeclarationJoined:  // stored document equal, nothing written
case vulkan.DeclarationUpdated: // stored document differed, overwritten
}
```

There is no strict form. A differing declaration always overwrites,
and the overwrite is the [VK0059](/errors/VK0059/) warn naming the
change as `old -> new`. A refusing form was built and reverted: a
service that refuses a differing config can never have its config
changed without redeploying it as accepting first, and nobody wants
that dance. One declaring service per group is a convention the log
makes visible, and the same line on every restart is the tell.
`Start` and `Bindings` keep their own rules: read once at creation,
and install / wait.

## Produce

```go
// PROPOSED — not shipped API.
requests, err := client.RegisterProducer[PaymentRequestedV1](ctx, "payments.requested",
	&vulkan.ProducerConfig{
		Message: &vulkan.MessageOptions{Timeout: 10 * time.Second},
	})
if err != nil {
	return err
}

produced, err := requests.Produce(ctx, &PaymentRequestedV1{OrderId: "order-812"}, nil)
```

`nil` options means the defaults, on `Produce` and `Consume` alike. Today
every `cfg` accepts `nil` but `ProduceOptions` is a value, so every
produce in the codebase carries `producer.ProduceOptions{}`; one rule
for every optional parameter. `ProducerConfig` declares nothing durable
(a producer has no row of its own) and is just this process's message
defaults and batching.

## Schedule

A schedule is a declaration that returns its handle, and the handle is
what you run, the same three calls as a consumer or a producer.

```go
// PROPOSED — not shipped API.
nightly, err := client.RegisterSchedule[ReportRequestedV1](ctx,
	vulkan.ScheduleSpec{Name: "nightly-report", Topic: "reports.requested", Cron: "0 3 * * *"},
	&ReportRequestedV1{Kind: "nightly"}, &vulkan.ScheduleConfig{
		Timeout:     time.Minute,
		Concurrency: vulkan.ConcurrencyExclusive,
	})
if err != nil {
	return err
}

return nightly.Schedule(ctx)
```

`Schedule` runs the system manager, as it does today. The schedule
producer is a fleet worker and it produces every registered schedule,
not just this one, so the verb's name is a bit deceptive: a program
that calls `nightly.Schedule` is running every worker in the fleet
without having said so. That was weighed against the alternative, a
handle with no run verb and `client.RunManager` as the only way to
make a schedule fire, and the symmetry won. A user who has learned
`Register` then `Consume` and `Register` then `Produce` gets
`Register` then `Schedule` and nothing new. Two things keep the
deception in check: the manager's own starting line says which owner
it runs under, and the deployment that only produces still has
`client.RunManager` by its real name. A program that registers a
schedule and exits has registered one that never fires until something
runs a manager.

`ScheduleSpec` exists because three adjacent strings is where a swap
stops being caught. `name` and `topic` transposed registers a schedule
named `reports.requested` that produces onto a topic called
`nightly-report`, with no error at any point until someone asks why
nothing arrived. Two strings (`group, topic` on the consumer) stay
positional. `nightly.Declaration` reports created / joined / updated
like the consumer's.

## Handles

`client.Topic("payments.requested")` does no I/O and cannot fail. It is
a name plus the client, and every verb on it resolves the name when
called:

```go
// PROPOSED — not shipped API.
orders := client.Topic("payments.requested")
data, err := orders.Get(ctx) // *vulkan.TopicData; (nil, nil) when not registered
err = orders.Rename(ctx, "payments.card-requested")
err = orders.Destroy(ctx, nil) // vulkan.ErrTopicNotFound if it is gone
```

`Get` is the snapshot read and the only comma-ok verb. Every other verb
returns the not-found error itself. Any name-keyed API works this way:
`Destroy` is one statement whose zero-rows-affected is the existence
check, atomically, and a `Get` before it would only add a window in
which the answer can change. `kubectl delete`, `sqs.DeleteQueue`, and
JetStream's `stream.DeleteConsumer(ctx, name)` are the same shape.

Two honest notes. JetStream's own `js.Stream(ctx, name)` is the other
design: it fetches the stream's info, returns not-found at
acquisition, and caches the row on the handle, which is why it then
needs both `CachedInfo()` and `Info(ctx)`. Pub/Sub's
`client.Subscription(id)` is the no-I/O design this page copies. Both
are legitimate; the no-I/O one was picked so a handle can never hold a
row that has gone stale and so a one-shot CLI verb is one round trip.
And a `client.GetSchedule(ctx, name)` returning the handle with its
row as sugar over `Schedule(name).Get(ctx)` would fit; it was left out
to keep one read path, and I'm not sure that is the right call for
scripts.

## Admin, resource by resource

Every block reads the same way: list the collection, name one, read
it, act on it.

```go
// PROPOSED — not shipped API.
// topics
topics, err := client.ListTopics(ctx)
orders := client.Topic("payments.requested")
data, err := orders.Get(ctx)
if err != nil {
	return err
}
if data == nil {
	data, err = client.RegisterTopic(ctx, "payments.requested", nil)
	...
}
err = orders.Migrate(ctx, 3)
health, err := orders.Health(ctx)
snapshot, err := orders.Metrics(ctx)
err = orders.Rename(ctx, "payments.card-requested")
err = orders.Destroy(ctx, nil) // refused unless ClientConfig.AllowDestroy
current, err := orders.CompactionHead(ctx, "device-7")
versions, err := orders.ListKeyMessages(ctx, "device-7", 20)

// groups hang off their topic
groups, err := orders.ListGroups(ctx)
group := orders.Group("charge-cards")
data, err := group.Get(ctx)
workers, err := group.ListWorkers(ctx)
err = group.Destroy(ctx, nil)
dead, err := group.ListDeadMessages(ctx, 50) // proposed verbs land here
err = group.Rewind(ctx, vulkan.AtTime(t))    // proposed

// schedules
schedules, err := client.ListSchedules(ctx)
nightly := client.Schedule("nightly-report")
data, err := nightly.Get(ctx)
err = nightly.Suspend(ctx)
err = nightly.Unsuspend(ctx)
result, err := nightly.Run(ctx, nil)
status, err := nightly.Status(ctx)
messages, err := nightly.ListMessages(ctx, 20)
err = nightly.Destroy(ctx)

// system -- the same handle grammar; today it takes no name
sys := client.System()
data, err := sys.Get(ctx)
err = client.RegisterSystem(ctx, nil)
err = sys.Migrate(ctx, 5)
err = sys.Destroy(ctx, nil)
```

A verb that returns a collection of a child resource is `List<Child>`
wherever it sits: `client.ListTopics`, `orders.ListGroups`,
`group.ListWorkers`, `nightly.ListMessages`. Every resource with
children has its list (today there is no way to list a topic's groups
at all), and a reader knows the return is a slice before reading the
signature. A read that returns a report keeps its own name: `Health`,
`Metrics`, `Status`.

The key read moves onto the topic. Today a compaction head is read
inside a transaction on the producer instance and outside one on a
separate `CompactionController` keyed by topic id, two objects for one
fact; `orders.CompactionHead` and `orders.ListKeyMessages` put the read
beside the topic that holds the row.

The system is a singleton today and a handle anyway. The day it gains
a name the API grows by one parameter: `client.RegisterSystem(ctx,
name, cfg)`, `client.System(name)`, topics nesting under it as
`client.System(name).Topic(name)` the way groups nest under topics, and
`client.Topic(name)` staying as the default system's shortcut. The
verbs that span a system's resources (`ListTopics`, `MigrateTopics`,
`ListBindingDeclarations`, `RunManager`) move with it that day; until then
they sit on the client.

## The manager

```go
// PROPOSED — not shipped API.
return client.RunManager(ctx)
```

The client holds the one `SystemManager`, so the refuse-a-second-Run
permit survives: today every `Schedule` call builds a fresh manager and
two calls in one process run two rival reconcile loops; under the
client the second is refused.

Nothing else on this page runs workers or stops running them. A
`Consume` already runs the fleet-wide workers beside its group's own
(the topic janitor, the schedule producer, the metrics collector), so
any process with one live consumer keeps upkeep running and fires
schedules. Admin verbs run nothing. The producer runs nothing, and
that is the one gap: a deployment that only produces accumulates
partitions with no log line saying why.

The `worker_liveness` alert closes it, the third built-in beside
`partition_count` and `compaction_read_cost`. Its condition is the
state the fleet already classifies: a worker row that wants instances
and has none live. Nothing is running it.

It reports the way both other built-ins do, once at register and once
on a schedule:

- `RegisterProducer` logs [VK0063](/errors/VK0063/) naming the topic,
  the unclaimed rows, and who declared them. The pass reads only:
  nothing is published, and `Register` never fails on it.
- Hourly under the manager, the check publishes an active alert to
  `__system.alerts` and resolves it once the rows are claimed again.
  `vulkan alert list` reads both states.

Worked case: `orders-api` runs only `RegisterProducer` on
`orders.placed`. Its register-time line names
`orders.placed (topic_janitor)`, so nothing is dropping that topic's
expired partitions. `fulfillment` starts its `Consume` on the
`pack-orders` group, its manager claims that row, and the next
`orders-api` restart is silent. Scale `fulfillment` to zero later and
the hourly check publishes the group itself:
`pack-orders (message_consumer, exception_consumer, cursor_advancer, manager)`.

One process that produces and then consumes trips the register-time
line once on a cold start, because `Register` runs before `Consume`
claims anything. An instance row lingers 30 seconds past its last
heartbeat, so a restart inside that window finds the old rows still
live and says nothing; a longer gap logs one line and clears itself.

## Testing your code

Handles are the seam. The package publishes a narrow interface for each
typed instance a handler or service holds, `vulkan.Producer[T]`
(`Produce`, `ProduceFunc`, `ProduceInTx`) and `vulkan.Consumer[T]`
(`Consume`), satisfied by the concrete instances, so a unit test
injects a fake and never opens a pool. For everything that needs the
real library, `vulkantest.NewClient(t)` runs it against an ephemeral
schema on the developer's Postgres and drops it at cleanup. The client
itself stays concrete; a test that wants to fake the whole client
defines the subset it uses.

## Names

The handle is the bare noun and the row a user reads takes `Data`:
`vulkan.Topic` is what you act on, `vulkan.TopicData` is what `Get`
returns. The read-models rename in one sweep (`topic.Topic` ->
`vulkan.TopicData`, `schedule.Schedule` -> `vulkan.ScheduleData`,
`worker.Worker` -> `vulkan.WorkerData`, `producer.MessageRow[T]` ->
`vulkan.MessageData[T]`), all or nothing, since a half-sweep leaves two
grammars. JSON is unaffected; the wire names live in field tags. A
typed instance exposes the row its declaration resolved as
`Registered` and its outcome as `Declaration`.

`Data` is the user's suffix, so the library's own layers give it up.
Today `*Data` names the table-exact scan structs in every datastore
package (`datastore.TopicData`, 63 of them); those become `*Row`,
named for the table they scan: `TopicConfigRow`, `WorkerConfigRow`,
`ScheduleConfigRow`. A scan destination is a row and its name now says
which table's, and `MessageRow` moving to `MessageData` is what frees
the suffix. `Info` was the first draft and was dropped: it is
JetStream's word, and a user reading `TopicData` needs no second
library to know what it is. The cost is a rename across every
datastore package for the users' sake, compile-time only.

## Worked case

`charge-cards` runs three replicas on `payments.requested` (topic id
`1`) with the default retry budget. A fourth service, `reconciliation`,
also consumes the group by mistake and declares `MaxRetries: 5`. Its
`RegisterConsumer` overwrites the stored document, its logger warns
[VK0059](/errors/VK0059/) with the `metadata` change as `old -> new`,
and the three replicas pick the new budget up on their next config
refresh. When the owning service next restarts it declares the default
again -> VK0059 again, the other way round -> and the budget flips on
every deploy of either service until someone reads the warn. Once `reconciliation` stops
declaring the group, the owning service redeclares `MaxRetries: 5`
deliberately and the row shows it:

```sql
SELECT w.name, w.metadata
FROM worker_config w
JOIN consumer_group_config g ON g.id = w.consumer_group_id
WHERE g.name = 'charge-cards';
--  name             | metadata
--  message_consumer | {"message": {"timeout": "10s", "retry": {"max_retries": 5}}, ...}
```

An operator checking the group from a script needs one round trip:

```go
// PROPOSED — not shipped API.
data, err := client.Topic("payments.requested").Group("charge-cards").Get(ctx)
```

## Open

- `GetSchedule`-style sugar returning a handle with its row, for
  scripts. Left out; see the handles section.
- The `Data` sweep is compile-time only but touches every read-model
  reference in the library, labs, and this site's samples, and every
  datastore scan struct on its way to `*Row`.
- `vulkan` becomes a large package: every config, options, spec,
  error, and read-model a user can name. That is the point of it, and
  also the cost.

Benchmark Methodology

Honest Numbers

How we benchmark a messaging system built on a general-purpose database — so that every number we publish is rerunnable, explained, and honest about what it cost.

01 · Position

Benchmarks are claims, and most claims don't survive an audit

The messaging space has a credibility problem. The public record of the last decade — the Kafka/Redpanda war,2,3 the Kafka/Pulsar durability dispute,5,6 databases benchmarked with persistence off7 — shows the same handful of sins repeating: acks that mean "in memory" compared against acks that mean "on disk", latency quoted from saturated runs, single workload points presented as generality, load generators benchmarking themselves.

This document is our defense. It fixes the method before any number exists: how a workload is defined, what environment it runs in, what gets measured, what makes a result valid, and how results are recorded so regressions are visible over time. It applies to any system in our category — a durable message queue built on a general-purpose database — where the database's own rhythms (checkpoints, vacuum, WAL flushes) are part of the system under test, not noise to be excluded.

The bar for publishing a number is that a skeptical engineer can rerun it with one command, see the raw data it came from, and read why it is what it is.

02 · Pipeline

Every result travels the same path

The two run modes exist because throughput and latency cannot come from the same run: at saturation, measured "latency" is just queue growth multiplied by run length.8 The validation gate exists because a plausible-looking number from an invalid run is worse than no number — it gets believed.

03 · Method

Fourteen rules

Each rule exists because someone, publicly and expensively, got burned without it. The failure it prevents is named beside it.

Workload
  1. R1
    Benchmark the public API — the code users actually run.
    Prevents: hand-copied SQL mirrors that silently go stale, and benchmark-only fast paths nobody would ship (the arms race that killed the TechEmpower leaderboard).9
  2. R2
    Declare the workload completely, and sweep every axis you claim generality over.
    Prevents: single-point cherry-picking — the 4-producer, keyless, fresh-disk configuration that flips to a loss at 50 producers with keys.2
Environment
  1. R3
    One pinned environment: same database image, same configuration, same resource caps for every bench; environment changes are versioned like code.
    Prevents: config drift read as performance change — kernel updates, image bumps, and default-config differences have all been published as "regressions".10,11
  2. R4
    Fingerprint every run: library commit, runtime and database versions, host facts — and the durability setting read back from the server, not echoed from the script.
    Prevents: uninterpretable year-old numbers, and the canonical messaging-benchmark foul — durability asymmetry, where an ack meaning "in page cache" is compared against an ack meaning "on disk".5,6
  3. R5
    Prove generator headroom: the load generator's own utilization is part of the result.
    Prevents: publishing the client's ceiling as the server's — the oldest mistake in the book, warned against by pgbench's own documentation.12
Measurement
  1. R6
    Two run modes, never conflated: saturation runs report throughput only; latency comes only from fixed-rate, open-loop runs below sustainable max.
    Prevents: latency-at-saturation, which measures queue depth times patience, not the system.8
  2. R7
    Sustainable max is operational: the highest rate on a stepped ladder at which the backlog stays bounded for the entire window.
    Prevents: burst-into-buffer "peak throughput" that no deployment can hold.5
  3. R8
    Measure latency from the intended send time; compute percentiles only from merged histograms; always show p50 through p99.9 and the max.
    Prevents: coordinated omission — a stalled system pausing its own measurement — and averaged percentiles, which are mathematically meaningless and systematically optimistic.8,13,14
  4. R9
    Measurement windows span the database's maintenance rhythms — at least one checkpoint cycle, with vacuum active — and record their counters as before/after deltas.
    Prevents: honeymoon runs measured before the first checkpoint storm, vacuum pass, or retention kick-in — where TPS is known to halve when the bill arrives.12,15,2
Validation
  1. R10
    Every run asserts its own premise, and warmup is verified from the recorded time series — a failed guard or an unstable window flags the run's record instead of averaging it in.
    Prevents: summarizing a run that never reached steady state — which careful measurement shows is the majority case, not the exception.4
  2. R11
    Every number names its limiter — the saturated resource, proven by counters captured during the run. No limiter, no publication.
    Prevents: "benchmarking A, measuring B, concluding C" — the passive-benchmarking trap. A number you can't explain is a number you can't trust.16
Recording & tracking
  1. R12
    Records are append-only and self-describing: raw per-interval samples, full parameters, and the fingerprint travel together in one record. Summaries are computed by tools, never by hand.
    Prevents: the one-number-per-run dead end — every pipeline that flattened results early foreclosed all later analysis; every one that kept raw samples could improve its statistics retroactively.17,18
  2. R13
    Repeat at the execution level: headline claims need at least three fresh executions; A/B claims interleave both arms in one session on one machine.
    Prevents: fictional error bars from a single lucky run, and slow environment drift masquerading as an effect.19,20,21
  3. R14
    The published writeup cites the raw records, prints the durability posture beside every number, and includes the workloads where we lose.
    Prevents: benchmarketing. Publishing the losing workload is the single strongest credibility signal a vendor can send.2,22
04 · Failure catalog

The named mistakes we design against

Every entry below has a public body count. The defense column cites the rules above.

MistakeHow the number liesDefense
Coordinated omission A closed-loop generator pauses whenever the system stalls, deleting exactly the worst samples before any percentile is computed. Tails come out orders of magnitude optimistic.8,13 R8
Latency at saturation Latency quoted from a max-throughput run measures queue growth times run length — a function of the test, not the system.8,5 R6 · R7
Averaged percentiles Per-interval or per-worker p99s averaged into a "global p99" — mathematically meaningless, always flattering.8 R8
The honeymoon run A window shorter than the database's checkpoint cycle, before vacuum debt or storage garbage collection comes due. Throughput can halve when it does.12,15,2 R9
Durability asymmetry Comparing an ack that means "in memory" against an ack that means "fsynced" — the axis behind every major messaging-benchmark war.3,5,6 R4 · R14
Generator as bottleneck The load generator saturates first and its ceiling is published as the server's.12 R5
Single-point cherry-pick One workload configuration — the one where you win — presented as general truth.2 R2 · R14
Assumed warmup A fixed discard prefix hides runs that never stabilized — or were actively degrading when the window closed.4 R10
The lucky run Best-of-N reported, no spread, no repetition at the level where variance actually lives.19 R12 · R13
Unexplained numbers A result with no bottleneck analysis — you benchmarked A, measured B, and concluded C.16 R11
Threshold alert floods Naive ">10% vs. baseline" regression gates produce ~99% false positives, then alert fatigue, then ignored real regressions.1 R12 · R13
Gamed benchmarks Benchmark-only code paths and tuning nobody would ship, optimizing the leaderboard instead of the product.9 R1
05 · Credibility

What every published result carries

These are the signals engineers consistently cite when they call a benchmark honest — and their absence is what they cite when they call one marketing.

✓
One-command rerun
From a clean machine to the same table, with the harness in the repo.
✓
Raw data in the repo
The records behind every chart, not just the chart.
✓
Full environment disclosure
Hardware, versions, and every non-default database setting, verbatim.
✓
Durability posture beside the number
What an ack survives, stated in the same table as the throughput.
✓
The time series, not just the aggregate
The checkpoint sawtooth and the vacuum dip are findings, not noise.
✓
A named limiter per number
The saturated resource, proven with counters from the run.
✓
Losing workloads included
The region of the workload space where we're slow, mapped honestly.
✓
Dated, versioned, append-only results
Claims expire; numbers are re-run per release, history is never rewritten.
06 · Lineage

Who we learned from

None of this is invented here. The method distills what the best pipelines converged on — and what the public failures taught everyone else.

Tracking pipelines

  • Go: benchfmt / benchstat / perf.golang.org — the standard result format; ratio-based noise defense
  • rustc-perf — per-benchmark noise-derived thresholds; the best long-range tracker running
  • Conbench (Apache Arrow) — identity-vs-informational metadata split; raw samples stored
  • MongoDB's change-point paper — why thresholds fail: the ~99% false-positive number
  • Hunter / Apache Otava — E-divisive change-point detection over results stored in a SQL database

Measurement methodology

  • Gil Tene — coordinated omission; HdrHistogram; "how not to measure latency"
  • Brendan Gregg — active benchmarking; the USE method; name the limiter
  • Barrett et al. — "VM Warmup Blows Hot and Cold": steady state must be verified
  • Kalibera & Jones — repetition at the level where variance lives
  • SIGPLAN guidelines — the empirical-evaluation checklist

Domain practice & cautionary tales

  • OpenMessaging Benchmark — the workload-spec vocabulary; the wars fought in its forks
  • Kafka vs. Redpanda — same tool, same hardware, opposite conclusions
  • pgbench good practices — short runs lie; scale vs. clients; rate mode done right
  • ClickBench — one-script reproduction; tuned entries labeled; limitations self-declared
  • TigerBeetle — the benchmark ships in the product; numbers as consequences of design
07 · References

Sources

Every claim above traces to one of these. The lineage section credits the systems we imitate; this list carries the specific evidence behind the numbers and the named failures.

  1. "The Use of Change Point Detection to Identify Software Performance Regressions in a Continuous Integration System" — Daly, Brown, Ingo, O'Leary & Bradford, ICPE 2020. Threshold-based alerting at roughly 1% actionability (2,393 tickets in five months in one project); change-point detection raised actionability to ~67%.
  2. "Kafka vs Redpanda Performance — Do the claims add up?" — J. Vanlightly, 2023. The teardown: producer-count cherry-picking, fresh-SSD honeymoon (p99.99 rising to 26s after 12h as drive GC kicked in), message keys flipping results, backlog-drain failure — and where each side wins.
  3. "Redpanda vs. Kafka" — Redpanda, 2022. The opposing methodology post: 30-minute warmups, hour-long measured runs, full hardware disclosure — and the Kafka fsync configuration later disputed.
  4. "Virtual Machine Warmup Blows Hot and Cold" — Barrett, Bolz-Tereick, Killick, Mount & Tratt, OOPSLA 2017. Under extreme environment control, only ~30–43.5% of (VM, benchmark) pairs consistently reached a steady state of peak performance; steady state is detected per-run with changepoint analysis, never assumed.
  5. "Benchmarking Apache Kafka, Apache Pulsar, and RabbitMQ: Which Is the Fastest?" — Confluent, 2020. Source of the fixed-rate latency methodology and the operational definition of sustainable throughput; its durability configuration was itself disputed in [6].
  6. "Benchmarking Pulsar and Kafka: A More Accurate Perspective on Pulsar's Performance" — StreamNative, 2020. The durability-matched re-run that reversed several of [5]'s results.
  7. "MongoDB Criticism Roundup" — InfoQ, 2011. Early MongoDB defaults: unacknowledged writes benchmarked as if durable.
  8. "How NOT to Measure Latency" and the wrk2 README — G. Tene. Coordinated omission, measuring from the intended send time, why latency at saturation is meaningless, and "you can't average percentiles — period."
  9. TechEmpower Framework Benchmarks sunsetting discussion — 2026. Benchmark-specialized non-idiomatic implementations and maintenance burden cited in the project's wind-down.
  10. "Tracing an unrelated benchmark regression" — CodSpeed engineering blog. A flagged "regression" traced to a glibc difference between CI runner images, not code.
  11. Change-point-detection evaluation on MooBench — arXiv:2510.11310, 2025. A detected change point traced to a kernel version change on GitHub-hosted runners.
  12. pgbench documentation, "Good Practices" — PostgreSQL. Runs must last minutes to hours for reproducibility; pgbench itself can be the bottleneck; -R schedules transactions and measures latency from the scheduled start time.
  13. "Open Versus Closed: A Cautionary Tale" — Schroeder, Wierman & Harchol-Balter, NSDI 2006. Open and closed workload models of the same system produce vastly different response-time behavior.
  14. HdrHistogram — G. Tene. Mergeable, full-fidelity latency histograms; the structure that makes honest percentiles possible.
  15. "Checkpoints, Write Storms, and You" — pgEdge. Checkpoint write storms saturating disk within seconds when shared buffers hold many dirty pages.
  16. "Active Benchmarking" — B. Gregg. Passive benchmarking yields "you benchmark A, but actually measure B, and conclude you've measured C"; profile while the benchmark runs and name the limiter.
  17. Conbench documentation — Apache Arrow's benchmarking framework. Raw per-repetition samples stored with summaries computed server-side; identity-forming vs. informational metadata split.
  18. rustc-perf comparison analysis — Rust. Per-benchmark significance thresholds derived from each series' own recent noise; per-iteration results stored raw.
  19. "Rigorous Benchmarking in Reasonable Time" — Kalibera & Jones, ISMM 2013. Variance lives at multiple levels (iteration, execution, build); repeat at the level that dominates or the error bars are fiction.
  20. benchstat — golang.org/x/perf. Median summaries, Mann-Whitney U comparison, ≥10 runs recommended, and "~" printed instead of a statistically unsupported delta.
  21. "Producing Wrong Data Without Doing Anything Obviously Wrong!" — Mytkowicz, Diwan, Hauswirth & Sweeney, ASPLOS 2009. Link order and environment size alone swing measured performance by up to ±10% — more than many published effects.
  22. ClickBench — ClickHouse. One-script reproduction from a clean VM, tuned entries labeled separately, and a self-declared limitations section.
